The Sentry Cloudflare SDK automatically propagates traces for incoming and outgoing HTTP requests if you've setup the SDK to send traces.

For RPC calls within Cloudflare (Worker-to-Durable Object, Worker-to-Worker via service bindings), you name the bindings that should carry the trace. See [RPC Trace Propagation](#rpc-trace-propagation) below.

For Cloudflare Queues, you name the producer bindings whose messages should carry the trace. See [Queue Trace Propagation](#queue-trace-propagation) below.

### RPC Trace Propagation

<AvailableSince version="10.52.0" />

By default, traces are not propagated across [RPC calls](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/) between Workers and Durable Objects. This is because [Cap'n Proto](https://capnproto.org/) (which powers Cloudflare RPC) has no native support for headers or metadata. The SDK carries the trace context in a trailing argument instead, and the receiving SDK strips it before your method runs.

That trailing argument is why propagation is opt-in per binding: only a Sentry-instrumented receiver strips it again. List the bindings whose receiver you know runs Sentry in `rpcTracePropagationBindings` (SDK version 10.72.0 or higher). Setting the option also turns on the receiver side, so a Worker that both calls and receives needs nothing else.

If you build with the <PlatformLink to="/install/vite-plugin/">Sentry Cloudflare Vite plugin</PlatformLink>, it derives the bindings that point at classes in this Worker, such as your own Durable Objects, and wraps those classes as receivers. Traces then connect across these RPC calls with no configuration. See <PlatformLink to="/install/vite-plugin/#derived-rpc-trace-propagation">Derived RPC Trace Propagation</PlatformLink>.

Bindings to other Workers stay opt-in. List them in your `instrument.server.ts` file. The plugin adds the derived bindings to your list:

```typescript {filename:src/instrument.server.ts}
import { defineCloudflareOptions } from "@sentry/cloudflare";

export default defineCloudflareOptions((env) => ({
  dsn: env.SENTRY_DSN,
  tracesSampleRate: 1.0,
  // Propagate to `env.AUTH_SERVICE` and every `env.SVC_*` binding
  rpcTracePropagationBindings: ["AUTH_SERVICE", /^SVC_/],
}));
```

The Worker behind each listed binding must also run Sentry, so that it strips the trace argument again.

If you deploy with `wrangler` directly, the plugin can't derive bindings. List every binding yourself, including bindings to your own Durable Objects, and set the option on the wrapped classes too, as shown in the <PlatformLink to="/install/wrangler/#instrument-durable-objects-workflows-and-agents">Wrangler setup</PlatformLink>.

Strings match a binding name exactly, so `"DB"` does not also match `MY_DB`. Use a regular expression for pattern matching. For the full definition, see <PlatformLink to="/configuration/options/#rpcTracePropagationBindings">`rpcTracePropagationBindings`</PlatformLink>.

<Alert level="warning" title="Only List Receivers You Control">
  A Worker that is not instrumented with Sentry never strips the trailing trace argument, so your method sees an extra parameter it was not called with. This is harmless for methods with fixed parameter lists, but changes behavior if your method uses rest parameters `(...args)` or reads `arguments.length`. Leave those bindings off the list.
</Alert>

The receiver continues the trace it is sent, creates a span per RPC method, and strips the trailing argument, so your method signatures are unaffected. Listing bindings on the receiver does no harm, so you can share one options object across the whole deployment.

### Queue Trace Propagation

<AvailableSince version="11.12.0" />

By default, the consumer of a [Cloudflare Queue](https://developers.cloudflare.com/queues/) starts a trace that isn't connected to the Worker that sent the message. To connect them, list the producer bindings in `queueTracePropagationBindings`:

```typescript {filename:src/instrument.server.ts}
import { defineCloudflareOptions } from "@sentry/cloudflare";

export default defineCloudflareOptions((env) => ({
  dsn: env.SENTRY_DSN,
  tracesSampleRate: 1.0,
  // Propagate to `env.BILLING_QUEUE` and every `env.JOBS_*` binding
  queueTracePropagationBindings: ["BILLING_QUEUE", /^JOBS_/],
}));
```

Queues have no message headers, so the producer adds its `sentry-trace` value to the message body under a `__sentry_queue_trace__` field. This only works for plain-object bodies. Arrays, binary data, and other values are sent unchanged, so their messages aren't linked.

The consumer doesn't need any configuration. A Sentry-instrumented consumer removes the field before your queue handler runs, so your handler sees the original body.

A batch can hold messages from unrelated traces, so the consumer doesn't continue any one of them. Instead, its `queue.process` span starts a new trace and links to the `queue.publish` span of every producer in the batch. Open the consumer's trace in Sentry to follow these links back to the producers.

<Alert level="warning" title="Only List Queues Whose Consumer Runs Sentry">
  A consumer that isn't instrumented with Sentry never removes the `__sentry_queue_trace__` field, so it arrives as part of the message body. The field also adds about 80 bytes to each message. Cloudflare [rejects messages over 128 KB](https://developers.cloudflare.com/queues/platform/limits/), so a message close to that limit can fail to send once you turn on propagation.
</Alert>

For the full definition, see <PlatformLink to="/configuration/options/#queueTracePropagationBindings">`queueTracePropagationBindings`</PlatformLink>.

### Custom Instrumentation

If you don't want to use the default tracing setup, you can set up <PlatformLink to="/tracing/trace-propagation/custom-instrumentation/">Custom Instrumentation</PlatformLink> for distributed tracing.

### Disabling Distributed Tracing

If you want to disable distributed tracing, set the `tracePropagationTargets` option to be an empty array. This will ensure no trace headers are sent.

```typescript {filename:src/instrument.server.ts}
import { defineCloudflareOptions } from "@sentry/cloudflare";

export default defineCloudflareOptions((env) => ({
  dsn: "___PUBLIC_DSN___",
  // Capture 100% of spans. This is useful for development and debugging. Consider reducing in production or using traceSampler
  tracesSampleRate: 1.0,
  // Overwrite the defaults to ensure no trace headers are sent
  tracePropagationTargets: [],
}));
```

### Trace Propagation Examples

#### Example 1: Microservices E-commerce Platform

```typescript {filename:src/instrument.server.ts}
import { defineCloudflareOptions } from "@sentry/cloudflare";

export default defineCloudflareOptions((env) => ({
  dsn: "___PUBLIC_DSN___",
  // Capture 100% of spans. This is useful for development and debugging. Consider reducing in production or using traceSampler
  tracesSampleRate: 1.0,
  tracePropagationTargets: [
    "https://api.myecommerce.com",
    "https://auth.myecommerce.com"
  ],
}));
```

This tells Sentry to pass trace headers across the following paths:

* Your main API server (where product data comes from)
* Your authentication server (where logins happen)

This way, if a customer experiences an error during checkout, or you want to check the performance of a specific endpoint, you can see the complete path their request took across these different services.

#### Example 2: Mobile App with Backend Services

```typescript {filename:src/instrument.server.ts}
import { defineCloudflareOptions } from "@sentry/cloudflare";

export default defineCloudflareOptions((env) => ({
  dsn: "___PUBLIC_DSN___",
  tracePropagationTargets: [
    "https://api.myapp.com",
    "https://media.myapp.com",
    /^\/local-api\//
  ],
}));
```

This configuration lets your app track user actions across:

* Your main API server (handles most app functions)
* Your media server (handles images, videos, etc.)
* Any local API endpoints in your app

If your app crashes while a user is uploading a photo, you can trace exactly where the problem occurred - in the app itself, the main API, or the media service.
