## Symfony Scheduler

<Alert>

Symfony Scheduler monitoring ships in the next release of `sentry/sentry-symfony` after `5.16.0`.

</Alert>

The Symfony SDK can monitor the recurring messages of the [Symfony Scheduler](https://symfony.com/doc/current/scheduler.html) 6.4 or later. It sends a check-in when a worker starts a recurring message, and another when the message finishes or fails. (Please note, this creates a Cron Monitor for every recurring message, which counts against your quota.)

Enable it in your bundle configuration:

```yaml {filename:config/packages/sentry.yaml}
sentry:
    scheduler:
        enabled: true
```

The monitor slug is the schedule name and a name for the message, for example `default-app-send-report`. The name is the full command for scheduled console commands, the service and method for scheduled services, and the class name for other messages. Slugs are cut to 50 characters. When more than one recurring message in a schedule has the same slug, none of them are monitored and the SDK logs a warning with the logger set in `sentry.options.logger`. To monitor them, give each one its own message class or command, or move it to another schedule.

Messages from a custom message provider are only known when they run, so they're monitored unless their slug matches a message added to the schedule directly.

Sentry creates each monitor from the message's schedule on its first check-in:

- `RecurringMessage::cron()` and `#[AsCronTask]` send the cron expression and its timezone.
- `RecurringMessage::every()` and `#[AsPeriodicTask]` send the interval when it's a whole number of minutes.
- Intervals of `1 day`, `1 week`, `1 month` or `1 year` (and months that divide a year, such as `3 months`) send a cron expression at the time of the trigger's `from` (or its first run) in its timezone, so the time of day stays the same across DST changes. Monthly intervals need that date to be on day 28 or earlier. When a run falls in the hour that a DST change skips, Symfony moves it and every later run to the next hour, and the SDK updates the monitor to the new time. With a jitter, the message isn't monitored from then on.
- With a jitter and no `from`, these intervals aren't monitored when the schedule provider builds a new schedule each time, or when a worker consumes the message from another transport, since the SDK can't tell when the interval started.
- A jitter widens the check-in margin to cover it.

The SDK doesn't send check-ins for schedules that Crons can't express or would read differently. This includes intervals under a minute, other intervals in days or weeks, such as `'2 days'`, unless the timezone is UTC or a fixed offset (`Etc/*`), cron expressions with `dragonmantank/cron-expression` older than 3.3.0, cron expressions that `dragonmantank/cron-expression` and Crons read differently (`W`, minute or hour lists that aren't in ascending order, minute lists with ranges or steps, single-value ranges with a step such as `5-5/2`, and the day-of-week ranges `0-0`, `7-7` and `0-7/2`), triggers that skip runs, such as excluded time ranges, and custom triggers.

When a `RedispatchMessage` or Messenger routing sends a message to another transport, the message is monitored when a worker consumes it there. Messages that the scheduler's worker handles itself, including ones sent to the `sync` transport, are monitored right away. Cancelled runs and messages of anonymous classes don't send check-ins.

Retries aren't reported. If the first attempt of a message on an async transport fails, its check-in is `error`, even when a retry succeeds.

Messages with a batch handler send `ok` when the batch is flushed, so a long batch can run past the monitor's max runtime.

To skip some recurring messages, list them under `excluded_messages`. An entry matches the message class, the command name or full command of a scheduled console command, the `@service::method` of a scheduled service, or the monitor slug. Entries wrapped in slashes, optionally followed by flags such as `/^reports-/i`, are regular expressions. The SDK ignores an invalid regular expression and logs a warning. Excluded messages don't count when the SDK checks for shared slugs.

```yaml {filename:config/packages/sentry.yaml}
sentry:
    scheduler:
        enabled: true
        excluded_messages:
            - App\Message\CleanupMessage
            - 'app:sync-search-index'
            - '/^reports-/'
```
