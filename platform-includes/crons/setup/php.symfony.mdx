## Symfony Scheduler

<Alert>

Symfony Scheduler monitoring ships in the next release of `sentry/sentry-symfony` after `5.15.0`.

</Alert>

The Symfony SDK can monitor the recurring messages of the [Symfony Scheduler](https://symfony.com/doc/current/scheduler.html) 6.4 or later. It sends a check-in when a worker starts a recurring message, and another when the message finishes or fails. (Please note, this creates a Cron Monitor for every recurring message, which counts against your quota.)

Enable it in your bundle configuration:

```yaml {filename:config/packages/sentry.yaml}
sentry:
    scheduler:
        enabled: true
```

The monitor slug is the schedule name and a name for the message, for example `default-app-send-report`. The name is the full command for scheduled console commands, the service and method for scheduled services, and the class name for other messages. Slugs are cut to 50 characters. When more than one recurring message in a schedule has the same slug, none of them are monitored and the SDK logs a warning. To monitor them, give each one its own message class or command, or move it to another schedule.

Messages from a custom message provider are only known when they run, so they're monitored unless their slug matches a message added to the schedule directly.

Sentry creates each monitor from the message's schedule on its first check-in:

- `RecurringMessage::cron()` and `#[AsCronTask]` send the cron expression and its timezone.
- `RecurringMessage::every()` and `#[AsPeriodicTask]` send the interval when it's a whole number of minutes.
- Intervals of `1 day`, `1 week`, `1 month` or `1 year` (and months that divide a year, such as `3 months`) send a cron expression at the time of the trigger's `from` (or its first run) in its timezone, so the time of day stays the same across DST changes. Monthly intervals need that date to be on day 28 or earlier.
- A jitter widens the check-in margin to cover it.

The SDK doesn't send check-ins for schedules that Crons can't express or would read differently. This includes intervals under a minute, other intervals in days or weeks, such as `'2 days'`, unless the timezone has no DST, cron expressions with `W`, triggers that skip runs, such as excluded time ranges, and custom triggers.

`RedispatchMessage` isn't monitored; the message it redispatches is monitored when a worker consumes it. Messages that Messenger routes to another transport are monitored the same way. Retried messages, cancelled runs, and messages of anonymous classes don't send check-ins.

To skip some recurring messages, list them under `excluded_messages`. An entry matches the message class, the command name or full command of a scheduled console command, the `@service::method` of a scheduled service, or the monitor slug. Entries wrapped in slashes are regular expressions. Excluded messages don't count when the SDK checks for shared slugs.

```yaml {filename:config/packages/sentry.yaml}
sentry:
    scheduler:
        enabled: true
        excluded_messages:
            - App\Message\CleanupMessage
            - 'app:sync-search-index'
            - '/^reports-/'
```
