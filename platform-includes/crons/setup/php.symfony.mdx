## Symfony Scheduler

The Symfony SDK can monitor messages run by the [Symfony Scheduler](https://symfony.com/doc/current/scheduler.html). It sends a check-in when a recurring message starts, and another when it finishes or fails. (Please note, this creates a Cron Monitor for every recurring message, which counts against your quota.)

This requires `sentry/sentry-symfony` 5.14.0 or later and `symfony/scheduler` 6.4 or later.

Enable it in your bundle configuration:

```yaml {filename:config/packages/sentry.yaml}
sentry:
    scheduler:
        enabled: true
```

Sentry creates each monitor from the message's schedule on its first check-in:

- Cron expressions are sent with their timezone. Expressions that Sentry can't parse, such as `W`, `?`, or ranges that wrap around like `22-2`, are not monitored.
- Intervals are sent when they're a whole number of minutes.
- Triggers with a jitter get a larger check-in margin to cover it.
- Messages with any other trigger, including triggers that exclude a time range, are not monitored.
- `RedispatchMessage` is not monitored. The message it redispatches is monitored when a worker consumes it.
- Retried messages and messages replayed from a failure transport don't send check-ins.

The monitor slug comes from the message:

- Scheduled console commands use the command, for example `app:send-report --force` becomes `app-send-report-force`.
- Scheduled services use the service and method.
- Other messages use the class name, for example `SendDailyReportMessage` becomes `send-daily-report-message`. If the message has a `__toString()` method, its value is added at the end.
- Messages on a schedule other than `default` get the schedule name as a prefix.
- Slugs longer than 50 characters are shortened and end with a hash.

Messages of the same class share a monitor, even if they're scheduled with different arguments or schedules. To give each one its own monitor, implement `__toString()` on the message so that it returns a different value for each.
