The Unity SDK captures C# errors on every platform it supports. On most platforms, it also includes a native SDK that captures native crashes, such as crashes in the Unity engine or in native plugins. Native support is on by default.

## Supported Platforms

| Platform                           | Native crashes | Native SDK                                                          | Requirements                                        |
| ---------------------------------- | -------------- | ------------------------------------------------------------------- | --------------------------------------------------- |
| Android                            | Yes            | sentry-java with the NDK integration                                | IL2CPP                                              |
| iOS                                | Yes            | sentry-cocoa                                                        |                                                     |
| Windows (x64, x86)                 | Yes            | sentry-native with Crashpad, or the experimental Native backend     |                                                     |
| macOS                              | Yes            | sentry-cocoa, or sentry-native with the experimental Native backend | IL2CPP for sentry-cocoa                             |
| Linux (x86_64, ARM64)              | Yes            | sentry-native with Breakpad, or the experimental Native backend     |                                                     |
| Xbox, PlayStation, Nintendo Switch | Yes            | See <PlatformLink to="/game-consoles/">Game Consoles</PlatformLink> |                                                     |
| WebGL                              | No             |                                                                     |                                                     |
| visionOS, UWP                      | No             |                                                                     | Best effort: no offline caching or session tracking |

The SDK supports Unity 2021.3 and later. Dedicated server builds for Windows, macOS, and Linux get the same native support as players. On consoles, the SDK supports Xbox with the GDK, PlayStation 5, Nintendo Switch, and Nintendo Switch 2. The SDK doesn't support PlayStation 4, Xbox One without the GDK, tvOS, Embedded Linux, or Cloud Rendering.

## Scope Sync

The SDK syncs the scope you set in C# to the native SDK, so native crashes include it. It syncs:

- Breadcrumbs
- Tags
- Extras
- User
- Environment
- Trace
- Attachments

Some scope data doesn't reach native crashes:

- Custom contexts you set through `scope.Contexts`. The SDK only syncs the contexts it collects itself, such as device and app data.
- Attachments on iOS, and on macOS with the default Cocoa backend.
- With <PlatformLink to="/native-support/unity-as-a-library/">Unity as a Library</PlatformLink>, the app's own SDK owns part of the scope. On iOS, that's the user, environment, and trace. On Android, it's the trace, and the user when the game runs in the app's process.
- On Android, setting `NdkScopeSyncEnabled` to `false` turns off scope sync for NDK crashes.

## Mobile

The native crash support for Android and iOS is provided by adding platform-specific SDKs to the generated Xcode and Gradle projects at build time.

On Android, `NdkIntegrationEnabled`, `NdkScopeSyncEnabled`, `AndroidTombstoneEnabled`, and `AndroidReportHistoricalTombstones` control the NDK integration and tombstone reporting. On iOS, `IosWatchdogTerminationIntegrationEnabled` controls watchdog termination reporting. Learn more in <PlatformLink to="/configuration/options/">Options</PlatformLink>.

### Initialization of the Native SDKs

The [iOS SDK](/platforms/apple/guides/ios/) and [Android SDK](/platforms/android/) are capable of self-initializing before the Unity engine itself is started. This allows us to capture bugs/crashes happening within the engine itself.
There are three initialization types:

- `NativeInitializationType.Runtime`: Native SDKs initialize during runtime alongside the C# SDK
- `NativeInitializationType.BuildTime`: Native SDKs initialize before Unity engine starts
- `NativeInitializationType.External`: The app that embeds the game provides and initializes the native SDKs, when using <PlatformLink to="/native-support/unity-as-a-library/">Unity as a Library</PlatformLink>

Set the type with the `AndroidNativeInitializationType` and `IosNativeInitializationType` options in an [options configuration script](/platforms/unity/configuration/options/programmatic-configuration/). Both default to `Runtime`.

### Runtime Initialization (Default)

With runtime initialization, the native SDKs are initialized at runtime alongside the C# SDK. This allows all options to be dynamically configured through C# code during execution.

#### Android

At build time, the SDK modifies the generated Gradle project to include the Android SDK but sets `io.sentry.auto-init` in the `AndroidManifest.xml` to `false`. The Unity SDK will then initialize the Android SDK when it initializes itself.

#### iOS

At build time, the SDK modifies the generated Xcode project to include the iOS SDK but will not modify the `main.mm` file or write the options to file. The Unity SDK will then initialize the iOS SDK when it initializes itself.

### Build Time Initialization

When using build time initialization, the native SDKs are configured during build time and initialize before the Unity engine starts. This means the options are baked into the outputted projects and cannot be modified at runtime via C# code. Changes to properties like `Release` and `Environment` will not apply to events generated by the native SDKs.

#### Android

The SDK modifies the generated Gradle project to include the Android SDK. At build time, it will also write the options to the `AndroidManifest.xml`. These options cannot be changed at runtime. Changes to the options in the configuration callback will not affect the Android SDK.

#### iOS

The SDK modifies the generated Xcode project to include the iOS SDK. It adds the initialization code to the `main.mm` and generates the options provided by the editor configuration window as `SentryOptions.m`. The SDK also copies the `SentryNativeBridge` that enables the C# layer to communicate with the iOS SDK. This means that there's no need to use the Unity [built-in crash reporting](https://docs.unity3d.com/ScriptReference/CrashReport.html) functionality.

The [iOS SDK](/platforms/apple/guides/ios/) supports capturing Objective-C exceptions which are disabled in the generated Xcode project by default. Consider enabling them in the "Build Settings" tab by setting `GCC_ENABLE_OBJC_EXCEPTIONS` to true.

### External Initialization

When your game runs inside an iOS or Android app with Unity as a Library, the app owns the native SDK. The Unity SDK doesn't bundle it and attaches to the one the app initialized. On Android, a game running in a separate process initializes it there. Learn more in <PlatformLink to="/native-support/unity-as-a-library/">Unity as a Library</PlatformLink>.

## Desktop

The native support is configured and enabled as early as possible by the C# layer, right after the Unity engine starts. This is slightly different from on mobile where we inject native initialization code that runs before the Unity engine runs.

Native support on Windows, Linux, and macOS with the Native backend writes files to disk. If you set `DisableFileWrite`, the SDK turns native support off on these platforms.

On Windows, Linux, and macOS, `NativeHandlerPath` sets where the SDK looks for the crash handler executable. Learn more in <PlatformLink to="/configuration/options/">Options</PlatformLink>.

### Windows

On Windows, the Unity SDK includes the [Native SDK](/platforms/native/) with the Crashpad backend, for both 64-bit (x64) and 32-bit (x86) players. Windows native crashes are captured through minidumps. At the end of the build, the SDK copies `crashpad_handler.exe`, `crashpad_wer.dll`, and `sentry-native.dll` next to the player. Include all three files when you ship your game.

With the experimental Native backend, which you can select with `options.Experimental.WindowsBackend = WindowsBackend.Native`, the SDK uploads crashes right away through the out-of-process `sentry-crash.exe` handler. The build copies `sentry-crash.exe`, `sentry-wer.dll`, and `sentry-native.dll` next to the player instead. Include all three files when you ship your game.

### macOS

By default, native support on macOS relies on the [macOS SDK](/platforms/apple/guides/macos/). Stackwalking happens in process. This Cocoa backend needs IL2CPP. With Mono, the SDK captures C# errors only.

With the experimental Native backend, which you can select with `options.Experimental.MacosBackend = MacosBackend.Native`, the SDK uses the [Native SDK](/platforms/native/) instead. It uploads crashes right away through the out-of-process `sentry-crash` handler, which the build copies next to the player, and it works with both IL2CPP and Mono.

### Linux

On Linux the Unity SDK includes the [Native SDK](/platforms/native/) with the Breakpad backend by default. A minidump is created in process and no handler executable is required. With the experimental Native backend, which you can select with `options.Experimental.LinuxBackend = LinuxBackend.Native`, the SDK uploads crashes right away through the out-of-process `sentry-crash` handler, which the build copies next to the player.

The Native SDK ships for `x86_64` and `ARM64`, and the build picks the one that matches the player's architecture. ARM64 is supported for dedicated servers built with IL2CPP on Unity 6000.3 and later. On both architectures, the Native SDK runs on distributions with older glibc versions, such as Ubuntu 22.04 and Debian 12.

## Debug Symbols

Sentry requires [debug information files](/platforms/unity/data-management/debug-files/) to symbolicate your crashes. The Unity SDK provides an automated upload functionality for those symbol files that rely on the [sentry-cli](/cli/). This is done transparently so you're not required to run `sentry-cli` manually. The symbol upload happens during Unity build in the editor. We've included the executables for Windows, macOS, and Linux as part of the Unity SDK package.

The automated debug symbols upload is enabled by default but requires configuration. Go to **Tools > Sentry > Editor** to enter the [Auth Token](https://sentry.io/orgredirect/organizations/:orgslug/settings/auth-tokens/), Organization Slug, and the Project Name. Note that the Unity SDK creates a file at `Assets/Plugins/Sentry/SentryCliOptions.asset` to store the configuration, that should **not** be made publicly available.

### iOS - dSYM

Debug information files on the iOS platform are called dSYM.

For Sentry to symbolicate your crash logs we need two types of files:

1. `dSYM` that the automated symbols upload will pick up at the end of the build process without further action required.
2. `BCSymbolMap` files that are created during the archiving process

The automated symbol upload will take care of the `BCSymbolMap` files by processing them during the archiving process.

### Manual Upload Using sentry-cli

If you don't want to rely on the automated symbol upload, you can run `sentry-cli` through the commandline. For that, you can use the provided executables from within the package or follow the [sentry-cli documentation](/cli/installation/) to make it available globally. To upload debug symbols, run it with:

<OrgAuthTokenNote />

```bash
sentry-cli --auth-token ___ORG_AUTH_TOKEN___ debug-files upload --org ___ORG_SLUG___ --project ___PROJECT_SLUG___ PATH_TO_SYMBOLS
```
