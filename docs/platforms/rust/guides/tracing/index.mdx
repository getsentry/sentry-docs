The Sentry SDK offers an integration for tokio's [tracing](https://github.com/tokio-rs/tracing) ecosystem that supports:

- Reporting `tracing` spans to Sentry as transactions and spans.
- Reporting `tracing` events to Sentry as logs.
- Reporting errors and panics with the correct trace correlation.
- Optionally, reporting `tracing` events to Sentry as errors, which create issues.

## Install

Add Sentry and the `tracing` dependencies to your `Cargo.toml`. The `tracing` feature enables the Sentry tracing integration.

```toml {filename:Cargo.toml}
[dependencies]
tracing = "0.1.41"
tracing-subscriber = "0.3.19"
sentry = { version = "{{@inject packages.version('sentry.rust') }}", features = ["tracing"] }
tokio = { version = "1.45.0", features = ["full"] }
```

## Configure

Initialize the Sentry SDK and register the Sentry layers to start sending `tracing` spans and logs to Sentry:

<Alert level="warning">

Macros like `#[tokio::main]` and `#[actix_web::main]` are not supported. Initialize the Sentry client before starting the async runtime, as shown below.

</Alert>

```rust {filename:main.rs}
use sentry::integrations::tracing::{LogLayer, SpanLayer};
use sentry::SentryFutureExt;
use tracing_subscriber::filter::LevelFilter;
use tracing_subscriber::prelude::*;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let _guard = sentry::init(
        sentry::ClientOptions::new()
            .dsn("___PUBLIC_DSN___")
            .maybe_release(sentry::release_name!())
            // Enable tracing and capture all traces and spans.
            // Reduce this sample rate in production, or remove it to disable tracing.
            .traces_sample_rate(1.0),
    );

    tracing_subscriber::registry()
        .with(tracing_subscriber::fmt::layer())
        // Capture INFO, WARN, and ERROR spans as Sentry transactions and spans.
        .with(SpanLayer::new().with_filter(LevelFilter::INFO))
        // Capture INFO, WARN, and ERROR events as Sentry logs.
        .with(LogLayer::new().with_filter(LevelFilter::INFO))
        .init();

    tokio::runtime::Builder::new_multi_thread()
        .enable_all()
        .build()?
        .block_on(async {
            // Bind async work to the current Sentry Hub.
            fail().bind_hub(sentry::Hub::current()).await;
        });

    Ok(())
}

#[tracing::instrument] // Capture a root span (transaction) around this function.
async fn fail() {
    tracing::info!("Doing work"); // Capture a log.
    let _span = tracing::info_span!("Child span").entered(); // Capture a child span.
    tracing::error!("Everything is on fire!"); // Capture a log linked to the child span.
}
```

## Verify Your Setup

Run the example above to send traces and logs to Sentry. Log into [sentry.io](https://sentry.io) and select your project. View the recorded traces and spans in **Explore > Traces**, and the recorded logs in **Explore > Logs**.

The example captures `tracing::error!` as a log. To also create an issue, enable the optional [error layer](#capture-errors-as-issues), then run the example again and select **Issues** in the sidebar.

## Customize Event Capture

The integration provides separate layers, so you can choose which `tracing` data to send to Sentry. We recommend enabling the span and log layers, as shown above:

- [`SpanLayer`](https://docs.rs/sentry-tracing/latest/sentry_tracing/struct.SpanLayer.html): Captures `tracing` spans as Sentry transactions and spans.
- [`LogLayer`](https://docs.rs/sentry-tracing/latest/sentry_tracing/struct.LogLayer.html): Captures `tracing` events as Sentry logs. Requires the `logs` feature, which is enabled by default.

The layers don't filter by level on their own, and without a filter they capture every level, including `DEBUG` and `TRACE`. We recommend giving each layer a `tracing_subscriber` filter, as shown above. `LevelFilter::INFO` is a sensible starting point for most applications.

<Alert level="warning">

`sentry::integrations::tracing::layer()` and `SentryLayer` are deprecated as of version `0.49.4`. When migrating, replace the legacy layer instead of adding the new layers alongside it: combining `SpanLayer` with the legacy layer can panic. See the [migration guide](https://docs.rs/sentry-tracing/~0.49/sentry_tracing/struct.SentryLayer.html) for details.

</Alert>

### Capture Errors as Issues

If you'd like Sentry issues for error-level `tracing` events, for example, to use them in issue alerts, you can also enable the error layer, [`ErrorLayer`](https://docs.rs/sentry-tracing/latest/sentry_tracing/struct.ErrorLayer.html), with an `ERROR` level filter:

```rust
use sentry::integrations::tracing::{ErrorLayer, LogLayer, SpanLayer};
use tracing_subscriber::filter::LevelFilter;
use tracing_subscriber::prelude::*;

tracing_subscriber::registry()
    .with(tracing_subscriber::fmt::layer())
    .with(SpanLayer::new().with_filter(LevelFilter::INFO))
    .with(LogLayer::new().with_filter(LevelFilter::INFO))
    // Capture ERROR events as Sentry errors
    .with(ErrorLayer::new().with_filter(LevelFilter::ERROR))
    .init();
```

With this setup, `ERROR` events are sent to Sentry as both logs and errors.

<Alert level="warning">

Events captured by `ErrorLayer` count toward your [error quota](/pricing/quotas/manage-event-stream-guide/), which is typically more expensive than logs. Always add a level filter: without one, `ErrorLayer` sends every `tracing` event as an error, including `DEBUG` and `TRACE`.

</Alert>

The SDK also provides [`BreadcrumbLayer`](https://docs.rs/sentry-tracing/latest/sentry_tracing/struct.BreadcrumbLayer.html), which adds `tracing` events as breadcrumbs to subsequent Sentry errors. It's mainly there to support legacy setups. We recommend `LogLayer` instead, since logs are sent whether or not an error occurs.
