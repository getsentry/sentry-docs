Ad blockers often block requests to Sentry, so your events never arrive. A tunnel is an endpoint on your own origin that forwards events to Sentry, and ad blockers let requests to your own origin through.

![Without a tunnel, ad blockers block requests to Sentry. With a tunnel, the browser sends them to your own origin, which forwards them to Sentry.](/img/tunnel-flow.svg)

## Setting Up the Tunnel

<AvailableSince version="11.13.0" />

The browser sends its events to a path on your own origin derived from the DSN, for example `/qpo967`, and your server forwards them to Sentry.

If your server doesn't run a Sentry JavaScript SDK, or you want the tunnel as a route in your app, [set up the tunnel manually](#setting-up-the-tunnel-manually) instead.

<Alert level="warning">
  The tunnel only works while the server SDK is enabled. Without a DSN, or with
  `enabled: false`, the browser's events are lost.
</Alert>

<StepConnector selector="h3">

### Turn On the Tunnel in the Browser

Set `tunnel: true` in your browser `Sentry.init`:

<PlatformSection supported={["javascript.nextjs"]}>

If you use the `tunnelRoute` option, remove it from `withSentryConfig`.

</PlatformSection>

<PlatformSection supported={["javascript.tanstackstart-react"]}>

If you use the `tunnelRoute` option, remove it from `sentryTanstackStart`.

</PlatformSection>

### Add the Integration to Your Server

Add `serveTunnelIntegration` to your server `Sentry.init`:

<PlatformContent includePath="configuration/tunnel-server-init" />

<PlatformSection notSupported={["javascript.astro", "javascript.nextjs", "javascript.nitro", "javascript.nuxt", "javascript.react-router", "javascript.remix", "javascript.solidstart", "javascript.sveltekit", "javascript.tanstackstart-react"]}>

Use the server that serves your app. The tunnel is on the same origin as your page. If a separate dev server like Vite serves your page locally, use a [fixed path](#using-a-fixed-path) and proxy it to your server.

</PlatformSection>

<PlatformSection notSupported={["javascript.azure-functions"]}>

No additional setup is needed. The server SDK answers tunnel requests before they reach your app, so your routes and middleware don't need any changes.

</PlatformSection>

<PlatformSection supported={["javascript.nextjs"]}>

On Vercel, `withSentryConfig` adds a route for the tunnel at build time instead, and your middleware (`proxy.ts` or `middleware.ts`) runs before that route. If your middleware blocks requests, for example ones without a session, use a [fixed path](#using-a-fixed-path) and exclude it in the `matcher`:

```typescript {filename:proxy.ts}
export const config = {
  matcher: ["/((?!monitoring|_next/static|_next/image|favicon.ico).*)"],
};
```

</PlatformSection>

<PlatformSection supported={["javascript.aws-lambda"]}>

The SDK answers tunnel requests when you load it with `NODE_OPTIONS`, as described in the [setup guide](/platforms/javascript/guides/aws-lambda/install/npm/), or wrap your handler with `Sentry.wrapHandler`. If you only call `Sentry.init` inside your handler module, tunnel requests reach your handler instead.

</PlatformSection>

<PlatformSection supported={["javascript.bun", "javascript.elysia"]}>

Call `Sentry.init` before you create your server, for example by preloading your instrument file with `bun --preload`. A server created before `init` doesn't answer tunnel requests.

</PlatformSection>

<PlatformSection supported={["javascript.deno"]}>

Call `Sentry.init` before you create your server, by importing your instrument file before anything else. A server created before `init` doesn't answer tunnel requests.

</PlatformSection>

<PlatformSection supported={["javascript.cloudflare"]}>

If your Worker serves static assets with a single-page app fallback, Cloudflare answers the tunnel request before your Worker runs. Run your Worker first:

```jsonc {filename:wrangler.jsonc}
{
  "assets": {
    "not_found_handling": "single-page-application",
    "run_worker_first": true,
  },
}
```

</PlatformSection>

<PlatformSection supported={["javascript.azure-functions"]}>

The SDK can't answer tunnel requests on Azure Functions, because each function only gets the requests for its own route. Set `intercept: false`, and answer them with `handleTunnelRequestIfMatched` in a function with a catch-all route:

```javascript
Sentry.init({
  dsn: "___PUBLIC_DSN___",
  integrations: [Sentry.serveTunnelIntegration({ intercept: false })],
});
```

</PlatformSection>

To check the tunnel, trigger an event and look in your browser's Network tab for a `POST` to a path on your own origin that returns `200`.

</StepConnector>

### Using a Different DSN in the Browser

The server answers one path per DSN it allows. If your browser uses a different DSN than your server, add it to `allowedDsns`:

<PlatformSection notSupported={["javascript.cloudflare"]}>

```javascript
Sentry.init({
  dsn: "___PUBLIC_DSN___",
  integrations: [
    Sentry.serveTunnelIntegration({
      allowedDsns: ["<your browser DSN>"],
    }),
  ],
});
```

</PlatformSection>

<PlatformSection supported={["javascript.cloudflare"]}>

```javascript
export default Sentry.withSentry(
  (env) => ({
    dsn: "___PUBLIC_DSN___",
    integrations: [
      Sentry.serveTunnelIntegration({
        allowedDsns: ["<your browser DSN>"],
      }),
    ],
  }),
  {
    async fetch(request, env, ctx) {
      // Your app
    },
  }
);
```

</PlatformSection>

### What the Tunnel Forwards

- Only events for your server's DSN and your `allowedDsns`, so the tunnel can't be used as an open proxy.
- The visitor's real IP address, without cookies or auth headers.

## Setting Up the Tunnel Manually

The browser setup works the same as for the automatic tunnel, except that you point the browser SDK to the tunnel path you want to use, for example `/tunnel`:

```javascript
Sentry.init({
  dsn: "___PUBLIC_DSN___",
  tunnel: "/tunnel",
});
```

How you serve that path depends on your server. If it runs a Sentry JavaScript SDK, you can use the tunnel helpers it comes with. Otherwise, write the endpoint yourself.

### With a Sentry JavaScript SDK on Your Server

Keep `serveTunnelIntegration` on your server. Set `intercept: false` so your route answers the requests instead of the SDK, and set `path` to your route so tunnel requests stay out of your traces:

<PlatformSection notSupported={["javascript.cloudflare"]}>

```javascript
Sentry.init({
  dsn: "___PUBLIC_DSN___",
  integrations: [
    Sentry.serveTunnelIntegration({ intercept: false, path: "/tunnel" }),
  ],
});
```

</PlatformSection>

Answer the requests at your endpoint with `handleTunnelRequest`, which forwards them to Sentry:

<PlatformContent includePath="configuration/tunnel-manual-route" />

To forward a different browser DSN, add it to `allowedDsns` on the integration, as described in [Using a Different DSN in the Browser](#using-a-different-dsn-in-the-browser). `handleTunnelRequest` uses the same list.

### On Other Servers

Your endpoint must:

- Forward the request body to Sentry, without cookies or auth headers.
- Accept only envelopes for your own DSNs, so it can't be used as an open proxy.
- Send the envelope only to the host of that DSN.

<Expandable title="Example endpoints">

```csharp {tabTitle:ASP.NET Core}
// This functionality is now built-in to the Sentry.AspNetCore package.
// See https://docs.sentry.io/platforms/dotnet/guides/aspnetcore/#tunnel
// docs for more information.

// This example shows how you could implement it yourself:

using System;
using System.Collections.Generic;
using System.IO;
using System.Net.Http;
using System.Text.Json;
using Microsoft.AspNetCore;
using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Hosting;
using Microsoft.AspNetCore.Http;

// Change host appropriately if you run your own Sentry instance.
const string host = "sentry.io";
// Set knownProjectIds to a list with your Sentry project IDs which you
// want to accept through this proxy.
var knownProjectIds = new HashSet<string>() {  };

var client = new HttpClient();
WebHost.CreateDefaultBuilder(args).Configure(a =>
    a.Run(async context =>
    {
        context.Request.EnableBuffering();
        using var reader = new StreamReader(context.Request.Body);
        var header = await reader.ReadLineAsync();
        var headerJson = JsonSerializer.Deserialize<Dictionary<string, object>>(header);
        if (headerJson.TryGetValue("dsn", out var dsnString)
            && Uri.TryCreate(dsnString.ToString(), UriKind.Absolute, out var dsn))
        {
            var projectId = dsn.AbsolutePath.Trim('/');
            if (knownProjectIds.Contains(projectId) && string.Equals(dsn.Host, host, StringComparison.OrdinalIgnoreCase)) {
              context.Request.Body.Position = 0;
              await client.PostAsync($"https://{dsn.Host}/api/{projectId}/envelope/",
                  new StreamContent(context.Request.Body));
            }
        }
    })).Build().Run();
```

```ruby {tabTitle:Rails}
require 'net/http'

class HomeController < ApplicationController

  SENTRY_HOST = "oXXXXXX.ingest.sentry.io"
  SENTRY_PROJECT_IDS = ["123456"]

  def tunnel
    envelope = request.body.read
    piece = envelope.split("\n").first
    header = JSON.parse(piece)
    dsn = URI.parse(header['dsn'])
    project_id = dsn.path.tr('/', '')

    raise "Invalid sentry hostname: #{dsn.hostname}" if dsn.hostname != SENTRY_HOST
    raise "Invalid sentry project id: #{project_id}" unless SENTRY_PROJECT_IDS.include?(project_id)

    upstream_sentry_url = "https://#{SENTRY_HOST}/api/#{project_id}/envelope/"
    Net::HTTP.post(URI(upstream_sentry_url), envelope)

    head(:ok)
  rescue => e
    # handle exception in your preferred style,
    # e.g. by logging or forwarding to server Sentry project
    Rails.logger.error('error tunneling to sentry')
  end

end
```

</Expandable>

#### Credentials on Tunnel Requests

The browser sends cookies and HTTP authentication to an endpoint on the same origin as your app. If your endpoint forwards request headers, it sends them on to Sentry.

Forward only the request body, or tell the browser to send no credentials:

```javascript
Sentry.init({
  dsn: "___PUBLIC_DSN___",
  tunnel: "/tunnel",
  transportOptions: {
    fetchOptions: { credentials: "omit" },
  },
});
```

If a layer in front of your tunnel requires credentials, like Vercel Deployment Protection or Cloudflare Access, keep sending them and forward only the request body.
