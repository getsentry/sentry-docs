To monitor errors and performance in web views of React Native applications, you set up Sentry SDKs in both the mobile application and the web projects running in the web views. You can also connect their traces, so a single distributed trace spans your React Native app and the web content it embeds.

## Application Monitoring

To monitor errors and performance in the React Native part of the application, follow the [Sentry React Native SDK setup instructions](/platforms/react-native/). The React Native SDK doesn't capture errors that happen inside a web view — those are captured by the JavaScript SDK running in the web project (see [WebView Monitoring](#webview-monitoring)).

## WebView Monitoring

To monitor errors and performance in web views, choose the appropriate Sentry JavaScript SDK depending on the framework used in the web project.

- [Sentry React Native SDK](/platforms/react-native/) (if the web project uses React Native Web or Expo)
- [Sentry React SDK](/platforms/javascript/guides/react/) (if the web project uses React)
- [Other Sentry JavaScript SDKs](/platforms/javascript/)

## Connect Traces

<Alert>

`sentryWebViewProps` is available from React Native SDK version `8.32.0`.

</Alert>

Use `sentryWebViewProps` to inject the React Native app's trace into a web view. The Browser SDK running in the web page picks it up on pageload and continues the same trace, so the web page's pageload transaction and errors share the trace of your React Native app. The result is a single connected trace across the native and web parts of the user journey.

Spread the props it returns onto your [`react-native-webview`](https://github.com/react-native-webview/react-native-webview) `<WebView>`:

```jsx
import { sentryWebViewProps } from "@sentry/react-native";
import { WebView } from "react-native-webview";

<WebView
  source={{ uri: "https://example.com" }}
  {...sentryWebViewProps({ allowedHosts: ["example.com"] })}
/>;
```

For the connection to take effect:

- The web page must run a Sentry [Browser SDK](/platforms/javascript/) with tracing enabled (the `browserTracingIntegration`). It continues the trace from the injected `sentry-trace` and `baggage` `<meta>` tags automatically — no additional configuration is needed on the web page.
- `allowedHosts` declares the hosts you trust to load in this WebView. A page is matched when its hostname equals an entry or is a subdomain of it (for example, `"example.com"` matches both `example.com` and `app.example.com`). Matching is case-insensitive, and the trace context is only written on matching pages.

<Alert level="info">

On iOS the trace tags are written before any page script runs. On **Android**, `react-native-webview` injects them asynchronously as the page starts, so they can land slightly after the page's first synchronous `<head>` scripts. Load and initialize `@sentry/browser` the usual way — from a `<script>` tag, a bundle, or an `async`/deferred init — so it reads the tags after they're present. A `@sentry/browser` initialized synchronously inline at the very top of `<head>` may run before the tags exist on Android and start a new trace instead of continuing (the WebView simply gets its own trace; nothing else is affected).

</Alert>

<Alert level="warning">

Only list hosts whose content you trust in `allowedHosts`. The trace context is injected into every matching page, so an allow-listed page that runs untrusted JavaScript can read it back and feed misleading or polluted data into the connected trace. This risk is bounded by `allowedHosts` — don't allow-list pages that render untrusted or third-party content.

`allowedHosts` is also checked inside the WebView page as defense-in-depth for honest cross-host navigation, but it is **not a strict security boundary**, since a hostile page sharing the WebView could bypass an in-page check.

The injected trace context carries no secrets or PII by default: the root span name (`sentry-transaction`), which can contain parameterized URLs, is stripped from `baggage` before it is injected. Still, don't put sensitive data in `baggage` for WebViews that may load untrusted pages.

</Alert>

<Alert level="info">

If you provide your own `onMessage` handler, spread `sentryWebViewProps` **first** and set `onMessage` after it. The helper returns a no-op `onMessage`, which is required for injected JavaScript to run on Android.

If you provide your own `injectedJavaScriptBeforeContentLoaded`, concatenate it with the one returned by `sentryWebViewProps` rather than overriding it. The prop is a single string, so setting your own after the spread replaces Sentry's injection and silently disables trace linking (and setting it before drops yours):

```jsx
const { injectedJavaScriptBeforeContentLoaded, onMessage } = sentryWebViewProps({
  allowedHosts: ["example.com"],
});

<WebView
  source={{ uri: "https://example.com" }}
  onMessage={onMessage}
  injectedJavaScriptBeforeContentLoaded={
    myScript + "\n" + injectedJavaScriptBeforeContentLoaded
  }
/>;
```

</Alert>

The trace is connected on the web page's initial load. Client-side navigations within a single-page app in the web view start their own traces, as they do in a regular browser.

The React Native app and the web project can report to different Sentry projects — as long as they're in the same organization, the trace view stitches the transactions together by trace ID.

## Notes

- The JavaScript SDK should be initialized when the web view is created and will be closed when the web view is closed. To monitor all web views in the application, initialize the JavaScript SDK every time a web view is created.

- If the web project is accessed remotely and not unique to the mobile application (for example the project also works as a standalone web application), we recommend using separate Sentry projects for the mobile application and the web project.
