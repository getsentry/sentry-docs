The .NET SDK provides an integration with [Hangfire](https://www.hangfire.io/) to monitor your jobs by automatically [creating check-ins for them](/product/monitors-and-alerts/monitors/crons/job-monitoring/). The SDK relies on job filters that are set up when you call `UseSentry`. For example:

```csharp
using Hangfire;
using Sentry.Hangfire;

GlobalConfiguration.Configuration.UseSentry();
```

Alternatively, if you're using the builder pattern, your code may look like this:

```csharp
using Hangfire;
using Sentry.Hangfire;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddHangfire(configuration => configuration
    .UseSentry() // <- Add Sentry to automatically send check-ins
);
```

To let the SDK know which jobs to monitor, you need to provide the job with a monitor slug. This can be done by setting the `SentryMonitorSlug` attribute on the job. For example, the following snippet shows how to set up a fire-and-forget job that Sentry will monitor:

```csharp
using Hangfire;
using Sentry.Hangfire;

GlobalConfiguration.Configuration.UseSentry();
BackgroundJob.Enqueue<PricingUpdateWorker>(job => job.Execute());

public class PricingUpdateWorker
{
    [SentryMonitorSlug("update-pricing")]
    public void Execute()
    {
        // Do your work to update the price
    }
}
```

The SDK will automatically capture a check-in with `CheckInStatus.InProgress` when the job starts and update the check-in with `CheckInStatus.OK` on success. In case of an exception during execution, the check-in will be updated as `CheckInStatus.ERROR` instead.

## Send the Recurring Job Schedule

Sentry only creates a monitor from a check-in that includes a monitor config. From the next SDK release, the SDK sends the schedule of your recurring jobs with their check-ins by default.

The job still needs the `SentryMonitorSlug` attribute, unless you [monitor all recurring jobs](#monitor-all-recurring-jobs).

```csharp
using Hangfire;
using Sentry.Hangfire;

GlobalConfiguration.Configuration.UseSentry();
RecurringJob.AddOrUpdate<PricingUpdateWorker>("update-pricing", job => job.Execute(), Cron.Hourly());

public class PricingUpdateWorker
{
    [SentryMonitorSlug("update-pricing")]
    public void Execute()
    {
        // Do your work to update the price
    }
}
```

The SDK sends the job's cron expression and time zone each time the job runs. Sentry creates the monitor on the first check-in and sets its schedule and time zone from the job on every check-in after that, so changes you make to those two settings in Sentry are overwritten. Other monitor settings are kept.

If Sentry doesn't support the job's cron expression or time zone, the check-in is sent without a schedule. This includes crons that run every few seconds, crons that restrict both the day of the month and the day of the week, and Windows time zone IDs on .NET Framework.

When you upgrade, existing monitors for recurring jobs get their schedule and time zone from the job. To keep managing the schedule in Sentry instead, turn off `SendMonitorConfig`:

```csharp
GlobalConfiguration.Configuration.UseSentry(options => options.SendMonitorConfig = false);
```

If you delete a monitor while its job still has `[SentryMonitorSlug]`, the next run creates it again. To stop monitoring a job, disable the monitor in Sentry, or remove the attribute.

## Monitor All Recurring Jobs

From the next SDK release, you can monitor every recurring job without adding the `SentryMonitorSlug` attribute to each one. Turn on `MonitorAllRecurringJobs`, and list any recurring job IDs you don't want to monitor in `ExcludedRecurringJobs`:

```csharp
GlobalConfiguration.Configuration.UseSentry(options =>
{
    options.MonitorAllRecurringJobs = true;
    options.ExcludedRecurringJobs.Add("cache-warmup");
});
```

The monitor slug is the recurring job ID in lowercase, with characters other than letters, digits, `-`, and `_` replaced by `-`, and cut to 50 characters. For example, the recurring job `Reports.Nightly Run` reports to the monitor `reports-nightly-run`. Jobs with the `SentryMonitorSlug` attribute keep their slug and are monitored even if their ID is excluded.

The schedule is sent as described in [Send the Recurring Job Schedule](#send-the-recurring-job-schedule). If two recurring jobs end up with the same monitor slug and different schedules, their check-ins are sent without a schedule. Jobs that aren't recurring, such as `BackgroundJob.Enqueue`, still need the attribute.
