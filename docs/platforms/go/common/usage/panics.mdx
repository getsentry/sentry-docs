Use `sentry.Recover(ctx, nil)` as a directly deferred call to recover and report a panic. The context selects the scope, client, and active trace.

## Recovering a Panic

Defer `Recover` in the function or goroutine that may panic. It must be deferred directly so Go's built-in `recover` can catch the panic:

```go
func handle(ctx context.Context) {
	defer sentry.Recover(ctx, nil)
	// Work that may panic.
}
```

Enable `AttachStacktrace` during initialization to include stack traces when the panic value is a string.

## Using Your Own Recovery Handler

If you already call Go's `recover`, pass the recovered value to Sentry. You can then re-panic or return an error response as appropriate:

```go
defer func() {
	if recovered := recover(); recovered != nil {
		sentry.Recover(ctx, recovered)
		// Optionally re-panic after recording the event.
		// panic(recovered)
	}
}()
```

The SDK delivers events asynchronously by default. Before process exit, flush the client with `sentry.ClientFromContext(ctx).Flush(5 * time.Second)`. For synchronous panic-event delivery, configure <PlatformLink to="/configuration/transports/#httpsynctransport">HTTPSyncTransport</PlatformLink>.

## Reading Context in BeforeSend

`EventHint.Context` defaults to the context passed to `Recover`. Use it in `BeforeSend` to read operation-specific values:

```go
sentry.Init(sentry.ClientOptions{
	Dsn: "___PUBLIC_DSN___",
	BeforeSend: func(event *sentry.Event, hint *sentry.EventHint) *sentry.Event {
		if hint.Context != nil {
			// Read your application's context values here.
		}
		return event
	},
})
```

Use the same context as your normal captures so panic reports carry the correct request scope and trace.
