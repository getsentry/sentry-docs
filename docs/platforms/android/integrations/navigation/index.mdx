The `sentry-android-navigation`, `sentry-android-navigation3`, and `sentry-compose-android` libraries provide support for Sentry's Android navigation instrumentation. Use them to automatically add breadcrumbs, track screen names, and start navigation transactions whenever users navigate around your app.

This page covers:

- **[Navigation 2](#classic-views)** for classic Views via `SentryNavigationListener`
- **[Navigation 2](#jetpack-compose)** for Jetpack Compose via `NavHostController.withSentryObservableEffect`
- **[Navigation 3](#navigation-3)** for Jetpack Compose via `SentryNavEffect`

## Navigation 2

`SentryNavigationListener` for [Navigation 2](https://developer.android.com/guide/navigation/) integrations lets you observe destination changes reported by your `NavController`. Upon every destination change the listener:

- starts a new navigation transaction and binds it to the current [Sentry scope](https://docs.sentry.io/platforms/android/enriching-events/scopes/)<sup>†</sup>
- emits a breadcrumb
- updates the currently tracked screen name

`SentryNavigationListener` can be used directly with [classic Views](#classic-views) or in wrapped form with [Jetpack Compose](#jetpack-compose).

<small>
  † A new navigation transaction will *not* be bound if another unfinished
  transaction is already bound to the current scope.
</small>

#### Configure

Registration of the `SentryNavigationListener` should happen in the appropriate lifecycle callbacks of the entity that owns your `NavController`:

```kotlin
import androidx.navigation.NavController
import io.sentry.android.navigation.SentryNavigationListener

private val navController = findNavController(R.id.nav_host)
private val sentryNavListener = SentryNavigationListener(
  enableNavigationBreadcrumbs = true, // enabled by default
  enableNavigationTracing = true  // enabled by default
)

override fun onResume() {
  super.onResume()
  navController.addOnDestinationChangedListener(sentryNavListener)
}

override fun onPause() {
  super.onPause()
  navController.removeOnDestinationChangedListener(sentryNavListener)
}
```

```java
import androidx.navigation.NavController;
import androidx.navigation.Navigation;
import io.sentry.android.navigation.SentryNavigationListener;

private final NavController navController = Navigation.findNavController(this, R.id.nav_host);
private final SentryNavigationListener navListener = new SentryNavigationListener(
  /* enableNavigationBreadcrumbs = */ true,
  /* enableNavigationTracing = */ true
);

@Override
protected void onResume() {
  super.onResume();
  navController.addOnDestinationChangedListener(sentryNavListener);
}

@Override
protected void onPause() {
  super.onPause();
  navController.removeOnDestinationChangedListener(sentryNavListener);
}
```

### Jetpack Compose

### Scrub Sensitive Info from the Recorded Breadcrumb/Transaction

`SentryNavigationListener` captures route arguments as additional data on breadcrumbs and transactions. If the arguments contain PII, you can strip them out with `BeforeBreadcrumbCallback` and `BeforeSendTransactionCallback`.<sup>†</sup>

To do so, [manually initialize](/platforms/android/manual-setup/#configuration-via-sentryoptions) the SDK and add the following snippet:

```kotlin
import io.sentry.android.core.SentryAndroid
import io.sentry.SentryOptions.BeforeBreadcrumbCallback
import io.sentry.SentryOptions.BeforeSendTransactionCallback
import io.sentry.android.navigation.SentryNavigationListener

SentryAndroid.init(this) { options ->
  options.beforeBreadcrumb = BeforeBreadcrumbCallback { breadcrumb, hint ->
    if (SentryNavigationListener.NAVIGATION_OP == breadcrumb.category) {
      breadcrumb.data.remove("from_arguments")
      breadcrumb.data.remove("to_arguments")
    }
    breadcrumb
  }

  options.beforeSendTransaction = BeforeSendTransactionCallback { transaction, _ ->
    val trace = transaction.contexts.trace
    if (SentryNavigationListener.NAVIGATION_OP == trace?.operation) {
      trace.setData("arguments", null)
    }
    transaction
  }
}
```

<small>
  † The snippet above removes route arguments, but it doesn't scrub route names.
  Define routes with stable names and placeholders, such as `profile/{user_id}`,
  and pass only sanitized values as arguments. Avoid putting PII directly in
  route names, as they can appear in breadcrumb `from` and `to` fields,
  transaction names, and screen names.
</small>

## Navigation 3

<Alert>

Navigation 3 support is available in `sentry-android-navigation3` `8.60.0` and later.

Review [Supported Setups](#supported-setups) and [Limitations](#limitations) before configuring `SentryNavEffect`.

</Alert>

Android's [Navigation 3 library](https://developer.android.com/guide/navigation/navigation-3) expects apps to manage their own back stack and to push and pop entries in order to navigate. `SentryNavEffect` instruments the back stack passed to your `NavDisplay`. By default, every time the top of the back stack changes, `SentryNavEffect` will:

- start a new navigation transaction and binds it to the current [Sentry scope](https://docs.sentry.io/platforms/android/enriching-events/scopes/)<sup>†</sup>
- emit a breadcrumb
- update the currently tracked screen name
- record the latest 5 entries from the back stack as event context

See [Customize Nav3 Options](#customize-nav3-options) to learn how to modify those defaults.

<small>
  † A new navigation transaction will *not* be started if another unfinished
  transaction is already bound to the current scope.
</small>

### Configure

To use `SentryNavEffect`, add it to the composable that owns your `NavDisplay` and pass your back stack to both:

```kotlin
import androidx.navigation3.runtime.NavKey
import androidx.navigation3.runtime.rememberNavBackStack
import androidx.navigation3.ui.NavDisplay
import io.sentry.compose.navigation3.BackStackEntryMapper
import io.sentry.compose.navigation3.SentryNavEffect
import kotlinx.serialization.Serializable

@Composable
fun AppNavigation() {
  // Create your back stack like usual.
  val backStack = rememberNavBackStack(Home)

  // Place SentryNavEffect in the same composable as your NavDisplay and call the
  // effect first.
  SentryNavEffect(
    backStack = backStack,
    // Choose the BackStackEntryMapper that best fits your needs.
    backStackEntryMapper = BackStackEntryMapper.SerialName,
  )

  // Configure your NavDisplay like usual.
  NavDisplay(
    backStack = backStack,
    ...
  )
}
```

**Note:** Be sure to call `SentryNavEffect` before `NavDisplay` so the effect's transaction-creating machinery can be set up before any spans are produced by the initial nav destination. Otherwise, initial destination spans may be lost or parented under the wrong transaction.

`BackStackEntryMapper` maps each back stack entry to a screen name and optional arguments. Choose a mapper:

| Mapper                                         | What Sentry Records                                                                                                                                                                             |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BackStackEntryMapper.SerialName`              | The entry's [serial name](https://kotlinlang.org/api/kotlinx.serialization/kotlinx-serialization-core/kotlinx.serialization.descriptors/-serial-descriptor/serial-name.html), without arguments |
| `BackStackEntryMapper.SerialNameAndProperties` | The entry's serial name and serialized properties as arguments                                                                                                                                  |
| A custom `BackStackEntryMapper`                | The name and arguments you specify (see [Choosing Which Arguments to Send](#choosing-which-arguments-to-send))                                                                                |

The built-in mappers require non-generic entry classes annotated directly with `@Serializable`. Custom `@MetaSerializable` annotations are not supported. Names come from `@SerialName`, or the fully qualified class name if no serial name is specified. Entries that can't be mapped appear as `/unknown`.

For custom mappers, keep names stable and arguments lightweight. Avoid `::class.simpleName`, which R8 obfuscates. A custom mapper can delegate entries that don't need special handling to `BackStackEntryMapper.SerialName.map(entry)` or `BackStackEntryMapper.SerialNameAndProperties.map(entry)`.

<Alert>

`SerialNameAndProperties` sends most properties unchanged, including personal data. It filters values whose property names match Sentry's sensitive denylist (such as `password` or `token`), but **does not scrub PII** such as email addresses. Neither `sendDefaultPii` nor `dataCollection` options change what it captures. Use it only if **all** your back stack entries are safe to send. Otherwise, use `SerialName` or a custom mapper that selects safe arguments.

Custom mapper values are not scrubbed by the SDK. Only return names and arguments known to be safe.

</Alert>

If you use `NavDisplay(entries = ...)` or `NavDisplay(sceneState = ...)`, pass `SentryNavEffect` the original back stack used to build the entries. Passing the `NavEntry` list to a built-in mapper records every destination as `/unknown`.

### Customize Nav3 Options

Use `SentryNavOptions` to disable breadcrumbs or transactions, or to limit how much of the back stack Sentry stores with captured events.

```kotlin
import io.sentry.compose.navigation3.SentryNavEffect
import io.sentry.compose.navigation3.SentryNavOptions

SentryNavEffect(
  backStack = backStack,
  ...
  options = SentryNavOptions {
    enableNavigationBreadcrumbs = true
    enableNavigationTransactions = true
    captureBackStack = true
    maxCapturedBackStackEntries = 5
  },
)
```

If you want to turn screen names on or off, configure the main SDK options when you initialize the Sentry SDK:

```kotlin
import io.sentry.android.core.SentryAndroid

SentryAndroid.init(this) { options ->
  options.isEnableScreenTracking = true
}
```

### Using kotlinx.serialization

If you use kotlinx.serialization with your navigation back stack, consider giving `@Serializable` entry types explicit `@SerialName` annotations for stable, readable destination names. Use a custom mapper to select arguments when entries are large, deeply nested, or contain sensitive information.

#### Choosing Which Arguments to Send

`BackStackEntryMapper.SerialNameAndProperties` uses kotlinx.serialization to convert the properties of each of your back stack entries into Sentry arguments. Values whose property names contain a term from [Sentry's sensitive denylist](https://develop.sentry.dev/sdk/foundations/client/data-collection/#sensitive-denylist) are replaced with `"[Filtered]"`. Matching is case-insensitive and can also filter harmless names, such as `keyword`, which contains `key`.

For example, given these entry types:

```kotlin
import androidx.navigation3.runtime.NavKey
import kotlinx.serialization.SerialName
import kotlinx.serialization.Serializable

@Serializable
enum class Source {
  @SerialName("search") SEARCH,
  @SerialName("deep_link") DEEP_LINK,
}

@Serializable
@SerialName("Cart")
data class Cart(
  val cartId: String,
  val source: Source,
  val userEmail: String,
  val authToken: String,
) : NavKey
```

Navigating to `Cart("7382rq", Source.DEEP_LINK, "jane@example.com", "abc123")` records `Cart` as the destination name, with these arguments:

```json
{
  "cartId": "7382rq",
  "source": "deep_link",
  "userEmail": "jane@example.com",
  "authToken": "[Filtered]"
}
```

`authToken` is filtered because it contains `auth`. `userEmail` is sent unchanged because the denylist targets credentials and secrets, not personal data.

To capture only `Cart`'s `cartId` and `source`, use a custom mapper. Delegate other entries to a built-in mapper only if their properties are safe to send:

```kotlin
import io.sentry.compose.navigation3.BackStackEntryMapper
import io.sentry.compose.navigation3.SentryBackStackEntry

val mapper = BackStackEntryMapper<NavKey> { entry ->
  when (entry) {
    is Cart -> SentryBackStackEntry(
      name = Cart.serializer().descriptor.serialName,
      arguments = mapOf("cartId" to entry.cartId, "source" to entry.source),
    )
    else -> BackStackEntryMapper.SerialNameAndProperties.map(entry)
  }
}
```

Use `BackStackEntryMapper.SerialName.map(entry)` as the fallback to record other entries without their properties.

Alternatively, wrap the built-in mapper and remove properties from the arguments it returns. Arguments use each property's `@SerialName`, or the property name if it has no annotation. For example, to remove `userEmail`:

```kotlin
val mapper = BackStackEntryMapper<NavKey> { entry ->
  BackStackEntryMapper.SerialNameAndProperties.map(entry)?.let { mapped ->
    SentryBackStackEntry(
      name = mapped.name,
      arguments = mapped.arguments?.filterKeys { it != "userEmail" },
    )
  }
}
```

<Alert>

Choosing the properties to send is safer than removing unwanted properties. If you add a property to an entry class later, this filtering approach sends it unless you also remove it.

</Alert>

Pass your custom mapper to `SentryNavEffect`:

```kotlin
SentryNavEffect(
  backStack = backStack,
  backStackEntryMapper = mapper,
)
```

#### Troubleshooting kotlinx.serialization Mappers

The built-in mappers record entries as `/unknown` when they can't determine a name. Enable the SDK's [`debug`](/platforms/android/configuration/options/#debug) option to see the reason. The first entry of each class that can't be named logs a warning.

**The entry class isn't `@Serializable` or is generic**

Annotate the class itself with `@Serializable`, or name it with a custom `BackStackEntryMapper`. The built-in mappers only check for `@Serializable` on the entry class. They don't name classes made serializable through a custom annotation marked [`@MetaSerializable`](https://kotlinlang.org/api/kotlinx.serialization/kotlinx-serialization-core/kotlinx.serialization/-meta-serializable/). For those classes, use a custom mapper that takes the name from the serializer, such as `MyRoute.serializer().descriptor.serialName`.

Generic classes, such as `SettingsScreen<T>`, require a custom mapper because their serializers need type arguments that can't be recovered at runtime.

**The entry's serializer throws**

If a custom serializer's initializer or `descriptor` throws, or a class the serializer needs can't be found, only entries of that class are affected. The warning includes the error.

If `SerialNameAndProperties` can determine a name but can't encode the properties, it keeps the name and drops the arguments. Enable `debug` to see the warning, logged once per entry type.

**The entry class has a named companion object, and the app uses R8**

With kotlinx.serialization older than `1.10.0`, R8 can remove information needed to look up serializers for entry classes with named companion objects, such as `companion object Factory`. Upgrade kotlinx.serialization to `1.10.0` or later, or add its [named-companion rules](https://github.com/Kotlin/kotlinx.serialization#android) to `proguard-rules.pro`. Replace the example class names with your serializable classes that have named companions:

```proguard {filename:proguard-rules.pro}
-keepattributes InnerClasses

-if @kotlinx.serialization.Serializable class
com.example.HasNamedCompanion,
com.example.HasNamedCompanion2
{
    static **$* *;
}
-keepnames class <1>$$serializer {
    static <1>$$serializer INSTANCE;
}

# R8 full mode also needs this rule.
-keepclasseswithmembers, allowshrinking, allowobfuscation, allowaccessmodification class
com.example.HasNamedCompanion,
```

**The app's kotlinx.serialization version is incompatible**

The built-in mappers require kotlinx.serialization `1.7.3` or later. If the app's version lacks or changes an API the mappers use, the SDK logs one warning and records entries that haven't been named yet as `/unknown`.

If your app meets the minimum version, upgrade the Sentry SDK. If you're already on the latest version, [open an issue](https://github.com/getsentry/sentry-java/issues/new/choose). Use a custom `BackStackEntryMapper` until the incompatibility is resolved.

### Supported Setups

The setups below require `sentry-android-navigation3` `8.62.0` or later. Earlier versions support only one active `SentryNavEffect` per [Sentry scope](/platforms/android/enriching-events/scopes/).

`SentryNavEffect` is compatible with most, but not all, Nav3 setups. Each effect uses the lifecycle of its nearest `LocalLifecycleOwner` to decide when it can write to Sentry's shared scope, and compatibility between effects depends on how those lifecycle owners interact. Incompatible effects won't crash, but they can generate stale navigation data, produce interleaved breadcrumbs, or interfere with each other's transactions.

**Supported:**

- A single-Activity app with one `NavDisplay` and `SentryNavEffect` pair.
- A multi-Activity app where each Activity has at most one `NavDisplay` and `SentryNavEffect` pair.
- A multi-Fragment app where each Fragment has at most one `NavDisplay` and `SentryNavEffect` pair (and the host Activity or Activities have no `SentryNavEffect`(s) of their own).
- A `ViewPager2` whose pages are Fragments, each with at most one `NavDisplay` and `SentryNavEffect` pair.
- An Activity or Fragment with its own `NavDisplay` and `SentryNavEffect` pair that stays visible beneath a `DialogFragment` or translucent Activity with its own pair.

<Alert>

All supported setups assume that each `SentryNavEffect` is called in the same composable as the `NavDisplay` it observes, and that the effect is called before it.

They also assume that `SentryNavEffect` is **_not_** called from content rendered by `NavDisplay`, such as a `NavEntry`, `NavEntryDecorator`, or `Scene`. (`SentryNavEffect` needs the lifecycle of the Activity or Fragment hosting a `NavDisplay`, rather than the navigation-scoped lifecycle that `NavDisplay` provides to its content.)

</Alert>

**Not supported:**

- Sibling `NavDisplay` and `SentryNavEffect` pairs in the same Activity or Fragment.
- Nested `NavDisplay` and `SentryNavEffect` pairs in the same Activity or Fragment. (If you nest `NavDisplay`s, consider using `SentryNavEffect` only with the outermost one.)
- `SentryNavEffect` instances in multiple Activities or Fragments that users can interact with at the same time, such as two Activities from the same app in [multi-resume mode](https://developer.android.com/develop/ui/views/layout/support-multi-window-mode#multi-resume), or an Activity and hosted Fragments where the Activity and Fragments each have their own `NavDisplay` and `SentryNavEffect` pairs.
- `SentryNavEffect` instances in pages or tabs that share their host's lifecycle, such as Compose `HorizontalPager` pages, `ViewPager2` pages that aren't Fragments, or tabs that are kept in the composition when inactive. Those pages or tabs share one `LifecycleOwner`, so at most one can call `SentryNavEffect`.

### Limitations

`SentryNavEffect` treats the top entry in your back stack as the current screen. That works well for most Nav3 setups, but it means that `SentryNavEffect` does **_not_**:

- understand the concept of Nav3 [Scenes](https://developer.android.com/guide/navigation/navigation-3/scenes) or multi-pane layouts
- track multiple back stacks with one `SentryNavEffect` instance
- make special accommodations for [predictive back](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture) gestures (e.g., spans produced by predictively rendered composables may appear under the current destination's transaction)

## Navigation 2 and Navigation 3 Interoperability

Navigation 2 and Navigation 3 can coexist in the same app. Their Sentry integrations observe navigation independently, but both write to the same Sentry scope by default.

If both integrations observe the same navigation flow – for instance, a Nav2 destination hosts a Nav3 flow – Sentry can receive duplicate breadcrumbs or conflicting screen names and transactions. Choose one integration to report each flow, or configure the integrations so they don't report the same data to the same scope.

If you're using the Sentry Android Gradle Plugin, be sure to account for automatically enabled Navigation 2 instrumentation when deciding which integration should report a flow.
