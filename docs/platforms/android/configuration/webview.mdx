To monitor errors and performance in web views of Android applications, you set up Sentry SDKs in both the mobile application and the web projects running in the web views. You can also connect their traces, so a single distributed trace spans your app and the web content it embeds.

## Application Monitoring

To monitor errors and performance in the native part of the application, follow the [Sentry Android SDK setup instructions](/platforms/android/). The Android SDK doesn't capture errors that happen inside a web view — those are captured by the JavaScript SDK running in the web project (see [WebView Monitoring](#webview-monitoring)).

## WebView Monitoring

To monitor errors and performance in web views, choose the appropriate Sentry JavaScript SDK depending on the framework used in the web project.

- [Sentry React SDK](/platforms/javascript/guides/react/) (if the web project uses React)
- [Sentry Angular SDK](/platforms/javascript/guides/angular/) (if the web project uses Angular)
- [Other Sentry JavaScript SDKs](/platforms/javascript/)

## Connect Traces

<Alert>

`SentryWebViewTracing` is available from Android SDK version `8.64.0`.

</Alert>

Use `SentryWebViewTracing.addTracePropagation` to inject your app's trace into an `android.webkit.WebView`. The Browser SDK running in the web page picks it up on pageload and continues the same trace, so the web page's pageload transaction and errors share the trace of your app. The result is a single connected trace across the native and web parts of the user journey.

Trace propagation uses the [AndroidX WebKit](https://developer.android.com/jetpack/androidx/releases/webkit) library, which the Android SDK doesn't add for you. Add it to your app:

```kotlin {filename:app/build.gradle.kts}
dependencies {
    implementation("androidx.webkit:webkit:1.14.0")
}
```

Then call `addTracePropagation` before the web view loads the page:

```kotlin {tabTitle:Kotlin}
import io.sentry.android.core.SentryWebViewTracing

SentryWebViewTracing.addTracePropagation(webView, "example.com")
webView.loadUrl("https://example.com")
```

```java {tabTitle:Java}
import io.sentry.android.core.SentryWebViewTracing;

SentryWebViewTracing.addTracePropagation(webView, "example.com");
webView.loadUrl("https://example.com");
```

You can pass several hosts, or a `List<String>`. Trace propagation applies to pages that start loading after the call. Call it from the main thread. The method returns `false` if nothing was added, for example when the `androidx.webkit` dependency is missing, the device's System WebView doesn't support it, no host is valid, the SDK isn't initialized, or it's called from another thread.

For the connection to take effect:

- The web page must run a Sentry [Browser SDK](/platforms/javascript/) with tracing enabled (the `browserTracingIntegration`). It continues the trace from the injected `sentry-trace` and `baggage` `<meta>` tags automatically, the same way it continues a trace started by a server (see [Distributed Tracing](/platforms/javascript/tracing/distributed-tracing/)) — no additional configuration is needed on the web page. The SDK writes the tags with a document-start script, before any page script runs, so the Browser SDK can be initialized anywhere in the page.
- The hosts you pass declare the hosts you trust to load in this web view. A page is matched when it's served over HTTPS and its hostname equals an entry or is a subdomain of it (for example, `"example.com"` matches both `example.com` and `app.example.com`). Matching is case-insensitive. Entries are normalized, so a scheme, path, trailing dot, or leading `*.` is ignored, and internationalized hostnames are converted to their ASCII form. A port other than `443` limits the entry to pages served on that port (for example, `"example.com:8443"`). The trace context is only written on matching pages, and only in the main frame, not in iframes.

<Alert level="warning">

Only list hosts whose content you trust. The trace context is injected into every matching page, so an allow-listed page that runs untrusted JavaScript can read it back and feed misleading or polluted data into the connected trace. This risk is bounded by the hosts you list — don't allow-list pages that render untrusted or third-party content.

The hosts are enforced by the web view and also checked inside the web page as defense-in-depth for honest cross-host navigation, but they're **not a strict security boundary**, since a hostile page sharing the web view could bypass an in-page check.

The injected trace context carries no secrets or PII by default: the root span name (`sentry-transaction`), which can contain parameterized URLs, is stripped from `baggage` before it is injected. Still, don't put sensitive data in `baggage` for web views that may load untrusted pages.

</Alert>

<Alert level="info">

The injected trace is a snapshot taken when you call `addTracePropagation`, and every later page load in that web view reuses it. To connect a later page load to a newer trace, call `addTracePropagation` again before the navigation. It replaces the script Sentry added earlier and keeps your own scripts.

</Alert>

### Set the Allowed Hosts in the SDK Options

To avoid listing the hosts on every call, set them once in the SDK options and call `addTracePropagation` without hosts:

```kotlin {tabTitle:Kotlin}
import io.sentry.android.core.SentryAndroid
import io.sentry.android.core.SentryWebViewTracing

SentryAndroid.init(context) { options ->
    options.webViewTracing.allowedHosts = listOf("example.com")
}

SentryWebViewTracing.addTracePropagation(webView)
webView.loadUrl("https://example.com")
```

```java {tabTitle:Java}
import io.sentry.android.core.SentryAndroid;
import io.sentry.android.core.SentryWebViewTracing;
import java.util.Collections;

SentryAndroid.init(context, options -> {
    options.getWebViewTracing().setAllowedHosts(Collections.singletonList("example.com"));
});

SentryWebViewTracing.addTracePropagation(webView);
webView.loadUrl("https://example.com");
```

You can also set them in your manifest, as a comma-separated list:

```xml {filename:AndroidManifest.xml}
<application>
    <meta-data
        android:name="io.sentry.webview-tracing.allowed-hosts"
        android:value="example.com,example.org" />
</application>
```

The list is empty by default, so without hosts `addTracePropagation(webView)` logs a warning and returns `false`. Hosts you pass to `addTracePropagation` are used instead of the ones in the options. The same matching rules and the warning above apply to both.

`allowedHosts` is separate from [`tracePropagationTargets`](/platforms/android/configuration/options/#tracePropagationTargets), which controls outgoing HTTP requests. Setting one doesn't affect the other.

### Connect Web Views Automatically

<Alert>

Automatic trace propagation is available from Android SDK version `8.65.0` and Sentry Android Gradle Plugin version `6.27.0`.

</Alert>

The [Sentry Android Gradle Plugin](/platforms/android/configuration/gradle/) can connect your web views without calls to `addTracePropagation`. It replaces each `WebView.loadUrl` call in your app with a call that refreshes the trace right before the page loads, so every page your app opens with `loadUrl` continues the trace that's active at that moment.

Enable the `WEBVIEW` instrumentation feature, which is off by default:

```groovy {filename:app/build.gradle}
import io.sentry.android.gradle.extensions.InstrumentationFeature

sentry {
  tracingInstrumentation {
    enabled = true
    features = EnumSet.allOf(InstrumentationFeature)
  }
}
```

```kotlin {filename:app/build.gradle.kts}
import java.util.EnumSet
import io.sentry.android.gradle.extensions.InstrumentationFeature

sentry {
  tracingInstrumentation {
    enabled.set(true)
    features.set(EnumSet.allOf(InstrumentationFeature::class.java))
  }
}
```

Then set the allowed hosts in the SDK options, as shown above. Without hosts, the plugin's change has no effect and pages are loaded as before.

- The plugin replaces `loadUrl` calls in your app and in its dependencies, including calls on `WebView` subclasses. The allowed hosts decide which pages receive the trace, so web views in your dependencies only receive it on hosts you listed.
- If you pass hosts to `addTracePropagation` for a web view, they're kept for that web view instead of the hosts in the options.
- Only `http` and `https` URLs refresh the trace. For example, `javascript:` URLs are loaded without it.
- Pages opened in other ways, such as links followed inside the page, `reload`, `postUrl`, or `loadDataWithBaseURL`, keep the trace from the last `loadUrl` call. `loadUrl` calls through a Java method reference, such as `webView::loadUrl`, and calls in minified dependencies aren't replaced.

### Pages Bundled With Your App

Pages loaded with `loadData`, with `loadDataWithBaseURL` and a base URL that isn't HTTPS, or from `file://` URLs don't receive the trace. To show pages bundled with your app, serve them over HTTPS with [`WebViewAssetLoader`](https://developer.android.com/reference/androidx/webkit/WebViewAssetLoader) and allow its domain:

```kotlin {tabTitle:Kotlin}
import android.webkit.WebResourceRequest
import android.webkit.WebResourceResponse
import android.webkit.WebView
import android.webkit.WebViewClient
import androidx.webkit.WebViewAssetLoader
import io.sentry.android.core.SentryWebViewTracing

val assetLoader =
    WebViewAssetLoader.Builder()
        .addPathHandler("/assets/", WebViewAssetLoader.AssetsPathHandler(context))
        .build()
webView.webViewClient =
    object : WebViewClient() {
        override fun shouldInterceptRequest(
            view: WebView,
            request: WebResourceRequest,
        ): WebResourceResponse? = assetLoader.shouldInterceptRequest(request.url)
    }

SentryWebViewTracing.addTracePropagation(webView, WebViewAssetLoader.DEFAULT_DOMAIN)
webView.loadUrl("https://${WebViewAssetLoader.DEFAULT_DOMAIN}/assets/index.html")
```

```java {tabTitle:Java}
import android.webkit.WebResourceRequest;
import android.webkit.WebResourceResponse;
import android.webkit.WebView;
import android.webkit.WebViewClient;
import androidx.webkit.WebViewAssetLoader;
import io.sentry.android.core.SentryWebViewTracing;

WebViewAssetLoader assetLoader =
    new WebViewAssetLoader.Builder()
        .addPathHandler("/assets/", new WebViewAssetLoader.AssetsPathHandler(context))
        .build();
webView.setWebViewClient(
    new WebViewClient() {
      @Override
      public WebResourceResponse shouldInterceptRequest(
          WebView view, WebResourceRequest request) {
        return assetLoader.shouldInterceptRequest(request.getUrl());
      }
    });

SentryWebViewTracing.addTracePropagation(webView, WebViewAssetLoader.DEFAULT_DOMAIN);
webView.loadUrl("https://" + WebViewAssetLoader.DEFAULT_DOMAIN + "/assets/index.html");
```

### Limitations

- Trace propagation requires an Android System WebView that supports document-start scripts (`WebViewFeature.DOCUMENT_START_SCRIPT`). On older WebViews, `addTracePropagation` returns `false` and the web page starts its own trace.
- Only `android.webkit.WebView` is supported, including a `WebView` shown with `AndroidView` in Jetpack Compose. Custom Tabs and Trusted Web Activities run in the browser app, so scripts can't be injected into them.
- Only HTTPS pages receive the trace.
- When no span is active, the injected trace doesn't carry a sampling decision, so the Browser SDK makes its own sampling decision for the web page.

The trace is connected on the web page's initial load. Client-side navigations within a single-page app in the web view start their own traces, as they do in a regular browser.

The app and the web project can report to different Sentry projects — as long as they're in the same organization, the trace view stitches the transactions together by trace ID.

## Notes

- The JavaScript SDK should be initialized when the web view is created and will be closed when the web view is closed. To monitor all web views in the application, initialize the JavaScript SDK every time a web view is created.

- If the web project is accessed remotely and not unique to the mobile application (for example the project also works as a standalone web application), we recommend using separate Sentry projects for the mobile application and the web project.
