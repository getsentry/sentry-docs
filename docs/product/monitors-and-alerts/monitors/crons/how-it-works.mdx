A cron monitor tracks one recurring job. Your job sends check-ins to Sentry, and Sentry compares them with the monitor's schedule to decide whether each run happened on time and succeeded.

## Check-Ins

A check-in reports the status of a single job run. Send one when the job starts (`in_progress`) and one when it finishes (`ok` or `error`). Use an [SDK](/product/monitors-and-alerts/monitors/crons/getting-started/), the [Sentry CLI](/cli/crons/), or [HTTP](/product/monitors-and-alerts/monitors/crons/getting-started/http/).

Sentry marks a run as:

- **Missed** if no check-in arrives within the check-in margin after the expected time.
- **Timed out** if the job sent `in_progress` but didn't finish within the max runtime.

If you only send a check-in when the job finishes (a heartbeat), Sentry still detects missed and failed runs, but it can't detect runs that hang.

**Send the same `check_in_id` with both check-ins for a run.** This tells Sentry which run a closing check-in belongs to, so overlapping or late runs aren't mixed up. SDK monitor helpers and `sentry-cli monitors run` do this for you. For HTTP, generate a UUID for each run.

## Schedules

- **Crontab schedules** (for example, `0 * * * *`): Sentry expects a check-in each time the expression matches, in the monitor's timezone (UTC by default).
- **Interval schedules** (for example, every 2 hours): Sentry expects the next check-in one interval after the last one it received.

If your scheduler starts the job at fixed clock times, use a crontab schedule, even for simple intervals.

## Issues and Recovery

Missed, failed, and timed-out runs count as failures. Sentry opens an issue once the monitor reaches its **failure tolerance** of failures in a row, and resolves it after its **recovery tolerance** of successful check-ins in a row. Both default to `1`. To get notified, connect an [Alert](/product/monitors-and-alerts/alerts/) to the monitor.

## Environments

Check-ins default to the `production` environment. Each environment shares the monitor's schedule and configuration but has its own status, check-ins, and issues. Once an environment sends a check-in, Sentry expects it on schedule, so [delete the environment](/product/monitors-and-alerts/monitors/crons/job-monitoring/#muting-and-deleting-environments) if the job stops running there.

## Limits and Defaults

| Setting                            | Default    | Limit                                                                                |
| ---------------------------------- | ---------- | ------------------------------------------------------------------------------------ |
| Schedule (`schedule`)              | Required   | Five-field crontab, or an interval. At most once a minute.                           |
| Check-in margin (`checkin_margin`) | 1 minute   | 1 to 40,320 minutes (28 days)                                                        |
| Max runtime (`max_runtime`)        | 30 minutes | 1 to 10,080 minutes (7 days)                                                         |
| Failure and recovery tolerance     | 1          | 1 to 720 check-ins                                                                   |
| Timezone (`timezone`)              | UTC        | Any [tz database](https://en.wikipedia.org/wiki/List_of_tz_database_time_zones) name |
| Monitor slug                       | —          | 50 characters                                                                        |
| Check-ins per monitor environment  | —          | 6 per minute. Extra check-ins are dropped.                                           |
| Check-in retention                 | —          | 90 days                                                                              |
