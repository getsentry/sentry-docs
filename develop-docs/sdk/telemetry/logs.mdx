<SpecMeta />

Logs are structured, timestamped messages that SDKs send to Sentry, linked to the trace in which they were captured. This spec defines the log wire format, the attributes SDKs attach to logs, how SDKs process and send logs, and the logger API.

## Scope

This spec applies to all SDKs that send logs to Sentry. Requirements that apply only to some SDKs, such as backend or mobile SDKs, say so.

## Definitions

- **Log**: an entry in the `items` array of a `log` envelope item.
- **Severity level**: one of `trace`, `debug`, `info`, `warn`, `error`, and `fatal`, from lowest to highest. These match [OpenTelemetry's severity text](https://opentelemetry.io/docs/specs/otel/logs/data-model/#field-severitytext). Each level corresponds to a range of [OpenTelemetry severity numbers](https://opentelemetry.io/docs/specs/otel/logs/data-model/#field-severitynumber): `trace` 1–4, `debug` 5–8, `info` 9–12, `warn` 13–16, `error` 17–20, `fatal` 21–24.
- **Parameterized log**: a log captured from a message template and parameters, such as the template `"User %s has logged in!"` with the parameter `"John"`. Its body is the template with the parameters substituted: `"User John has logged in!"`.
- **Auto-emitted log**: a log that an SDK captures without the user calling a Sentry logging API, for example by forwarding `console` calls or mirroring logs from Python's `logging` module.

## Requirements

<SpecSection id="log-envelope-item" status="stable" since="4.0.0">

### `log` Envelope Item

SDKs **MUST** send logs in `log` envelope items. An envelope **MUST NOT** contain more than one `log` item.

The item **MUST** have these headers:

| Header | Value |
|--------|-------|
| `type` | `"log"` |
| `item_count` | The number of logs in `items`. |
| `content_type` | `"application/vnd.sentry.items.log+json"` |

The item payload **MUST** be a JSON object whose `items` array contains the logs. The payload **MAY** also include the `version` and `ingest_settings` fields described in the next section.

A `log` item **MAY** contain logs from different traces. If it does, the envelope **MUST NOT** have a [DSC](/sdk/foundations/trace-propagation/dynamic-sampling-context/) header.

</SpecSection>

<SpecSection id="log-envelope-item-ingest-settings" status="candidate" since="1.17.0">

### `version` and `ingest_settings` properties

The `log` envelope item **SHOULD** include `version` and `ingest_settings` properties to instruct Relay to infer IP address and user agent from the incoming request. See the [Ingest Settings](/sdk/foundations/envelopes/envelope-items/#ingest-settings) spec for the full definition, field reference, and behavior.

</SpecSection>

<SpecSection id="log-payload" status="stable" since="4.0.0">

### `log` Envelope Item Payload

Each log in the `items` array is a JSON object with these fields:

| Field | Type | Required | Since | Description |
|-------|------|----------|-------|-------------|
| `timestamp` | Number | **REQUIRED** | 1.0.0 | Time the log was captured, in seconds since the Unix epoch. |
| `trace_id` | String | **REQUIRED** | 1.0.0 | 32-character hex trace ID. **MUST** be the trace ID of the propagation context that is current when the log is captured. |
| `level` | String | **REQUIRED** | 1.0.0 | The log's severity level. |
| `body` | String | **REQUIRED** | 1.0.0 | The log message. |
| `span_id` | String | **OPTIONAL** | 1.11.0 | 16-character hex span ID. See [Tracing Association](#tracing-association). |
| `severity_number` | Integer | **OPTIONAL** | 1.0.0 | Severity number. If sent, it **SHOULD** be the lowest number in the range of the log's severity level, for example `13` for `warn`. |
| `attributes` | Object | **OPTIONAL** | 1.0.0 | Attributes, each of which **MUST** declare its type, as specified in [Attributes](/sdk/foundations/state-management/scopes/attributes/). |

</SpecSection>

<SpecSection id="default-attributes" status="stable" since="4.0.0">

### Default Attributes

SDKs **MUST** attach these attributes to every log:

| Attribute | Since | Description |
|-----------|-------|-------------|
| `sentry.environment` | 1.0.0 | The environment set in the SDK. Omitted if not set. |
| `sentry.release` | 1.0.0 | The release set in the SDK. Omitted if not set. |
| `sentry.sdk.name` | 1.0.0 | The name of the SDK. |
| `sentry.sdk.version` | 1.0.0 | The version of the SDK. |
| `sentry.is_localhost` | 2.3.0 | Whether the SDK determined the application is running on localhost, which enables the localhost inbound filter. What counts as localhost is platform-specific; where applicable, SDKs **SHOULD** follow [Relay's detection heuristics](https://github.com/getsentry/relay/blob/master/relay-filter/src/localhost.rs). |

For parameterized logs, SDKs **MUST** also attach:

| Attribute | Since | Description |
|-----------|-------|-------------|
| `sentry.message.template` | 1.0.0 | The message template. |
| `sentry.message.parameter.<X>` | 1.0.0 | One attribute per parameter, where `<X>` is the parameter's position (`0`, `1`, …) or name (`item_id`, `user_id`, …). |

SDKs **MUST NOT** attach `sentry.message.template` to a log without `sentry.message.parameter.<X>` attributes (since 1.7.0).

Logs are billed by size. Apart from attributes set by the user, SDKs **SHOULD NOT** attach attributes to every log that this spec doesn't define.

</SpecSection>

<SpecSection id="sdk-integration-origin" status="stable" since="4.0.0">

### SDK Integration Origin

SDKs **SHOULD NOT** set `sentry.origin` on logs the user captures by calling a Sentry logging API. This deviates from [Trace Origin](/sdk/telemetry/traces/trace-origin/) to keep logs small.

On auto-emitted logs, SDKs **SHOULD** set `sentry.origin` as specified in Trace Origin, using:

- `auto.log.<name>` for logs mirrored from a logging library, for example `auto.log.serilog`.
- `auto.<category>.<integration-name>` for logs from other integrations, for example `auto.db.prisma`.

</SpecSection>

<SpecSection id="user-attributes" status="stable" since="4.0.0">

### User Attributes

SDKs **MAY** attach these attributes from the current user. SDKs **MUST NOT** attach them when `sendDefaultPii` is disabled, unless the user [set the data manually](/sdk/foundations/client/data-collection/#user-set-data-scrubbing) (since 2.1.0).

| Attribute | Description |
|-----------|-------------|
| `user.id` | The user ID. Maps to `id` in the [User](/sdk/foundations/transport/event-payloads/user/) payload. |
| `user.name` | The username. Maps to `username` in the [User](/sdk/foundations/transport/event-payloads/user/) payload. |
| `user.email` | The email address. Maps to `email` in the [User](/sdk/foundations/transport/event-payloads/user/) payload. |

</SpecSection>

<SpecSection id="user-agent-parsing" status="stable" since="1.5.0">

### User Agent Parsing

Relay derives `browser` and `os` information from the user agent of the request that delivers a log envelope. SDKs that don't forward a user agent **MAY** attach these attributes instead:

| Attribute | Description |
|-----------|-------------|
| `browser.name` | Display name of the browser. Maps to `name` in [Browser Context](/sdk/foundations/transport/event-payloads/contexts/#browser-context). |
| `browser.version` | Version string of the browser. Maps to `version` in [Browser Context](/sdk/foundations/transport/event-payloads/contexts/#browser-context). |

</SpecSection>

<SpecSection id="backend-attributes" status="stable" since="1.0.0">

### Backend SDK Attributes

Backend SDKs (Node.js, Python, PHP, etc.) **SHOULD** attach:

| Attribute | Description |
|-----------|-------------|
| `server.address` | The server address. Equivalent to [`server_name`](/sdk/foundations/envelopes/event-payloads/#optional-attributes) on errors and transactions. |

</SpecSection>

<SpecSection id="mobile-native-attributes" status="stable" since="1.5.0">

### Mobile, Desktop, and Native SDK Attributes

Mobile, desktop, and native SDKs (Android, Apple, Electron, etc.) **SHOULD** attach:

| Attribute | Description |
|-----------|-------------|
| `os.name` | OS name. Maps to `name` in [OS Context](/sdk/foundations/transport/event-payloads/contexts/#os-context). |
| `os.version` | OS version. Maps to `version` in [OS Context](/sdk/foundations/transport/event-payloads/contexts/#os-context). |
| `device.brand` | Device brand. Maps to `brand` in [Device Context](/sdk/foundations/transport/event-payloads/contexts/#device-context). |
| `device.model` | Device model. Maps to `model` in [Device Context](/sdk/foundations/transport/event-payloads/contexts/#device-context). |
| `device.family` | Device family. Maps to `family` in [Device Context](/sdk/foundations/transport/event-payloads/contexts/#device-context). |

</SpecSection>

<SpecSection id="tracing-association" status="stable" since="4.0.0">

### Tracing Association

If a log is captured while a span is active, SDKs **SHOULD** set its `span_id` to the active span's ID.

</SpecSection>

<SpecSection id="replay-association" status="stable" since="4.0.0">

### Replay Association

If a log is captured while a replay is active, SDKs **SHOULD** set the `sentry.replay_id` attribute to the active replay's ID. SDKs **MUST NOT** set `sentry.replay_id` if no replay is active.

</SpecSection>

<SpecSection id="log-ordering" status="candidate" since="1.16.0">

### Log Ordering

SDKs that target runtimes where timestamps may be frozen during synchronous execution (for example, Cloudflare Workers) or lack sub-millisecond precision **MUST** attach an integer `sentry.timestamp.sequence` attribute to every log. Other SDKs **MAY** omit it.

The value **MUST** be `0` for the first log captured after the SDK is initialized or re-initialized, and for any log whose timestamp falls in a different millisecond (`floor(timestamp * 1000)`) than the previous log's. Otherwise, it **MUST** be the previous log's value plus `1`.

The sequence orders logs only within a single SDK instance, not across processes or workers.

</SpecSection>

<SpecSection id="log-processing-pipeline" status="stable" since="4.0.0">

### Log Processing

SDKs **MUST** call `beforeSendLog` with each log only after attaching all attributes this spec defines, so that the callback can modify or remove them. If the callback returns `null`, SDKs **MUST NOT** send the log. Otherwise, they **MUST** send the log the callback returned.

</SpecSection>

<SpecSection id="buffering" status="stable" since="4.0.0">

### Buffering

SDKs **SHOULD** send logs in batches, not in one envelope per log. SDKs **MUST NOT** send more than 100 logs in one envelope (since 1.15.0).

SDKs **SHOULD** send all logs they haven't sent yet when the user flushes or closes the SDK and when the application shuts down gracefully, as in the [telemetry buffer data forwarding scenarios](/sdk/foundations/processing/telemetry-processor/#data-forwarding-scenarios).

SDKs **SHOULD** limit the number of logs waiting to be sent, and drop logs captured while that limit is reached.

</SpecSection>

<SpecSection id="data-category-rate-limiting" status="stable" since="4.0.0">

### Data Category and Rate Limiting

Logs belong to the `log_item` data category. SDKs **MUST NOT** send logs while the `log_item` category is [rate limited](/sdk/foundations/transport/rate-limiting/).

</SpecSection>

<SpecSection id="client-reports" status="stable" since="1.13.0">

### Client Reports

When SDKs discard logs, they **MUST** record [client report](/sdk/telemetry/client-reports/) entries for both the `log_item` (number of logs) and `log_byte` (size of the logs in bytes) categories. The size **MAY** be an approximation, such as the size the logs would have if serialized.

SDKs **MUST** record a client report in at least these cases:

- `before_send`: `beforeSendLog` returned `null`.
- `buffer_overflow`: the log was dropped because the [limit on logs waiting to be sent](#buffering) was reached.
- `ratelimit_backoff`: the log was dropped because the `log_item` category is [rate limited](#data-category-and-rate-limiting).
- `send_error`, `internal_sdk_error`, `network_error`: sending the envelope containing the log failed, as specified in [Network Failure Recording](/sdk/telemetry/client-reports/#network-failure-recording).

</SpecSection>

<SpecSection id="sdk-integrations" status="stable" since="4.0.0">

### SDK Integrations

SDKs **SHOULD** provide integrations that capture logs from platform logging libraries, such as JavaScript's `console`, Python's `logging`, or Java's Log4j.

</SpecSection>

<SpecSection id="auto-emitted-logs" status="candidate" since="3.0.0">

### Auto-Emitted Logs

Auto-emitted logs can cause unexpected volume and cost. SDKs **MUST NOT** send auto-emitted logs from an integration or library binding unless the user has explicitly enabled it, for example through an integration-specific option or by adding the integration explicitly.

</SpecSection>

<SpecSection id="debug-mode" status="stable" since="1.0.0">

### Debug Mode

If `debug` is enabled, calls to the logger API **SHOULD** also print the log to the console at the matching level.

</SpecSection>

<SpecSection id="initialization-options" status="stable" since="3.0.0">

### Initialization Options

SDKs **MUST** provide a `beforeSendLog` / `before_send_log` option. Its value is an optional callback that receives a log and returns it, a modified log, or `null` to drop it.

SDKs **SHOULD NOT** provide an API whose sole purpose is to disable all logs.

</SpecSection>

<SpecSection id="logger-api" status="stable" since="4.0.0">

### Logger Module

SDKs **SHOULD** provide a `logger` module or namespace with one method per severity level, such as `Sentry.logger.info`. SDKs **SHOULD** adapt the method names and signatures to their platform's conventions.

The methods **SHOULD** accept a message template and parameters, producing a parameterized log. They **MAY** also accept attributes.

Scopes and clients **SHOULD** provide a generic method for capturing a log, such as `captureLog`, and **SHOULD NOT** provide one method per severity level.

</SpecSection>

<SpecSection id="threading-concurrency" status="stable" since="4.0.0">

### Send Order

SDKs **MUST** send logs in the order they were captured.

</SpecSection>

## Implementation Guidance

**Buffering.** A simple strategy that satisfies [Buffering](#buffering) is to flush when the buffer holds 100 logs or 5 seconds have passed, and to hold at most 1000 logs.

**Background processing.** Logger methods return nothing, so SDKs can defer work such as template formatting and `beforeSendLog` to a background thread or queue. Doing so risks losing logs captured just before a crash, which matters most for mobile SDKs.
