## Overview

The Client supports several hook mechanisms for extensibility:

- **Lifecycle hooks** (`on`/`emit`) — an internal event subscription system primarily for integration authors
- **`before_send`** — a user-facing callback for modifying or discarding error events
- **`before_send_transaction`** — a user-facing callback for modifying or discarding transaction events
- **`before_send_check_in`** — an optional callback for modifying or discarding check-in events
- **`before_breadcrumb`** — a user-facing callback for modifying or discarding breadcrumbs

[Callback Error Isolation](#callback-error-isolation) applies to every user-provided callback, including those specified elsewhere: the `before_send_*` variants for each telemetry type, the samplers, and user-registered event processors.

Related specs:
- [Client](/sdk/foundations/client/) — event pipeline, event processors, and capture methods
- [Configuration](/sdk/foundations/client/configuration/) — `before_send`, `before_breadcrumb`, and sampler options
- [Client Reports](/sdk/telemetry/client-reports/) — discard reasons recorded when a callback drops an item

## Behavior

<SpecSection id="lifecycle-hooks" status="candidate" since="1.0.0">

### Lifecycle Hooks

The Client **SHOULD** support an event subscription system for fine-grained extensibility beyond `before_send` and event processors. This is primarily an internal API for integration authors. (See [RFC 0034](https://github.com/getsentry/rfcs/pull/34).)

```typescript
interface Client {
  on(hookName: string, callback: (...args: unknown[]) => void): void;
  emit(hookName: string, ...args: unknown[]): void;
}
```

Hooks are stateless and called in registration order. Data passed into hooks **MAY** be mutated by callbacks. Available hooks vary by SDK but may include:

- `startSpan` / `finishSpan` — span lifecycle
- `beforeEnvelope` — last chance to inspect/modify outgoing envelopes
- `startSession` / `endSession` — session lifecycle

This system complements — not replaces — the `before_send` hook and event processors. Use hooks when integrations need to react to lifecycle events that are not part of the event pipeline (e.g., span creation).

</SpecSection>

<SpecSection id="before-send-hook" status="stable" since="1.0.0">

### Before-Send Hook

Hook called with the event (and on some platforms the hint) that allows the user to decide whether an event should be sent or not. This can also be used to further modify the event. This hook **MUST** only apply to `error` events. Other event types like transactions, check-ins, and feedbacks **MUST NOT** go through `beforeSend` — they have their own dedicated hooks.

In the [event pipeline](/sdk/foundations/client/#event-pipeline), `before_send` is invoked after scope application and event processors, and before the session update. Returning `null` discards the event (client report reason: `before_send`).

</SpecSection>

<SpecSection id="before-send-transaction-hook" status="stable" since="1.0.0">

### Before-Send-Transaction Hook

Hook called with the transaction event (and on some platforms the hint) that allows the user to decide whether a transaction should be sent or not. This can also be used to further modify the transaction event. SDKs **SHOULD** support this hook.

This hook **MUST** only apply to transaction events. Returning `null` discards the transaction.

</SpecSection>

<SpecSection id="before-send-check-in-hook" status="stable" since="1.0.0">

### Before-Send-Check-In Hook

SDKs **MAY** implement a dedicated `beforeSendCheckIn` hook that applies only to check-in events. Check-in events **MUST NOT** go through the `beforeSend` hook.

See the <Link to="/sdk/telemetry/check-ins/#hooks">Check-Ins spec</Link> for full details.

</SpecSection>

<SpecSection id="before-breadcrumb-hook" status="stable" since="1.0.0">

### Before-Breadcrumb Hook

Hook called with the breadcrumb (and on some platforms the hint) that allow the user to decide whether and how a breadcrumb should be sent.

</SpecSection>

<SpecSection id="callback-error-isolation" status="candidate" since="1.1.0">

### Callback Error Isolation

A failing user callback **MUST NOT** break the host application. SDKs **MUST** catch every recoverable error a user-provided callback raises, for example with `try`/`catch` or `rescue`. A rejected promise, future, or task **MUST** be handled like a synchronous raise.

SDKs **SHOULD NOT** recover from intentionally fatal exits, such as Python's `KeyboardInterrupt` and `SystemExit`, Java `Error` subclasses like `OutOfMemoryError`, Rust panics, or C aborts. Recovering from them hides the underlying failure. SDKs whose callback types can't raise recoverable errors, checked at compile time, don't need a runtime boundary.

On failure, SDKs **MUST** emit an error-level [internal log](/sdk/foundations/client/configuration/#debug-mode) naming the callback, **MUST NOT** re-throw, and **MUST NOT** capture the error as an event or attach it to any telemetry. Like any internal log, it's only printed in debug mode; the `callback_error` client report is the signal in production. See [Never capture your own exceptions](/sdk/getting-started/principles/#never-capture-your-own-exceptions).

SDKs **SHOULD** offer an opt-in strict mode, disabled by default. In strict mode, a callback failure **MUST** propagate as an unhandled error of the host application instead of being isolated. SDKs **MUST NOT** pass the event reporting that error through the callback that failed.

SDKs **MUST** handle a failure as follows, not as if the callback had returned a value:

| Callback | On failure | Client report category |
|---|---|---|
| `before_send` | Drop the event | `error` |
| `before_send_transaction` | Drop the transaction | `transaction` (plus [span outcomes](/sdk/telemetry/client-reports/#span-outcomes)) |
| `before_send_log` | Drop the log | `log_item` (plus [`log_byte`](/sdk/telemetry/client-reports/#log-byte-outcomes)) |
| `before_send_metric` | Drop the metric | `trace_metric` (plus [`trace_metric_byte`](/sdk/telemetry/client-reports/#metric-byte-outcomes)) |
| `before_send_feedback` | Drop the feedback | `feedback` |
| `before_send_check_in` | Drop the check-in | `monitor` |
| `before_breadcrumb` | Drop the breadcrumb | None |
| `before_send_span` | Emit the original span | None |
| User-registered event processor | Drop the event | Category of the item |
| `traces_sampler` | Use the parent's decision, otherwise defer | None |
| `profiles_sampler` | Don't profile the transaction | None |

Filters drop the item because a callback that failed part-way may have skipped a redaction. `before_send_span` keeps the span because it enriches spans; [`ignore_spans`](/sdk/telemetry/spans/filtering/) is what filters them.

For a callback not listed here, SDKs **MUST** choose the outcome that sends less data. For example, if `before_capture_screenshot` fails, SDKs **MUST NOT** attach the screenshot.

If `traces_sampler` fails, SDKs **MUST** use the parent's sampling decision. Without a parent, they **MUST** leave the decision to downstream SDKs, as with tracing disabled, and **MUST NOT** fall back to `traces_sample_rate`. If `profiles_sampler` fails, SDKs **MUST NOT** profile the transaction.

SDKs **SHOULD** pass `before_send_span` a copy of the span, so they can emit the original if the callback fails. Otherwise, they **MUST** emit the span as it stands and skip the [`before_send_span` merge](/sdk/telemetry/spans/scrubbing-data/#scrubbing-data-with-beforesendspan).

A failure **MUST NOT** produce a billed event of any type. SDKs **MUST** record every item a failure drops with the [`callback_error`](/sdk/telemetry/client-reports/#discard-reasons) discard reason and the dropped item's category, so users can tell a failure apart from an explicit drop.

</SpecSection>
