## Overview

The Client supports several hook mechanisms for extensibility:

- **Lifecycle hooks** (`on`/`emit`) — an internal event subscription system primarily for integration authors
- **`before_send`** — a user-facing callback for modifying or discarding error events
- **`before_send_transaction`** — a user-facing callback for modifying or discarding transaction events
- **`before_send_check_in`** — an optional callback for modifying or discarding check-in events
- **`before_breadcrumb`** — a user-facing callback for modifying or discarding breadcrumbs
- **`error_sampler`** — an optional callback deciding the sample rate of an individual error event

[Callback Error Isolation](#callback-error-isolation) applies to every user-provided callback, including those specified elsewhere: the `before_send_*` variants for each telemetry type, the samplers, and event processors.

Related specs:
- [Client](/sdk/foundations/client/) — event pipeline, event processors, and capture methods
- [Configuration](/sdk/foundations/client/configuration/) — `before_send`, `before_breadcrumb`, and sampler options
- [Client Reports](/sdk/telemetry/client-reports/) — discard reasons recorded when a callback drops an item

## Behavior

<SpecSection id="lifecycle-hooks" status="candidate" since="1.0.0">

### Lifecycle Hooks

The Client **SHOULD** support an event subscription system for fine-grained extensibility beyond `before_send` and event processors. This is primarily an internal API for integration authors. (See [RFC 0034](https://github.com/getsentry/rfcs/pull/34).)

```typescript
interface Client {
  on(hookName: string, callback: (...args: unknown[]) => void): void;
  emit(hookName: string, ...args: unknown[]): void;
}
```

Hooks are stateless and called in registration order. Data passed into hooks **MAY** be mutated by callbacks. Available hooks vary by SDK but may include:

- `startSpan` / `finishSpan` — span lifecycle
- `beforeEnvelope` — last chance to inspect/modify outgoing envelopes
- `startSession` / `endSession` — session lifecycle

This system complements — not replaces — the `before_send` hook and event processors. Use hooks when integrations need to react to lifecycle events that are not part of the event pipeline (e.g., span creation).

</SpecSection>

<SpecSection id="before-send-hook" status="stable" since="1.0.0">

### Before-Send Hook

Hook called with the event (and on some platforms the hint) that allows the user to decide whether an event should be sent or not. This can also be used to further modify the event. This hook **MUST** only apply to `error` events. Other event types like transactions, check-ins, and feedbacks **MUST NOT** go through `beforeSend` — they have their own dedicated hooks.

In the [event pipeline](/sdk/foundations/client/#event-pipeline), `before_send` is invoked after scope application and event processors, and before the session update. Returning `null` discards the event (client report reason: `before_send`).

</SpecSection>

<SpecSection id="before-send-transaction-hook" status="stable" since="1.0.0">

### Before-Send-Transaction Hook

Hook called with the transaction event (and on some platforms the hint) that allows the user to decide whether a transaction should be sent or not. This can also be used to further modify the transaction event. SDKs **SHOULD** support this hook.

This hook **MUST** only apply to transaction events. Returning `null` discards the transaction.

</SpecSection>

<SpecSection id="before-send-check-in-hook" status="stable" since="1.0.0">

### Before-Send-Check-In Hook

SDKs **MAY** implement a dedicated `beforeSendCheckIn` hook that applies only to check-in events. Check-in events **MUST NOT** go through the `beforeSend` hook.

See the <Link to="/sdk/telemetry/check-ins/#hooks">Check-Ins spec</Link> for full details.

</SpecSection>

<SpecSection id="before-breadcrumb-hook" status="stable" since="1.0.0">

### Before-Breadcrumb Hook

Hook called with the breadcrumb (and on some platforms the hint) that allow the user to decide whether and how a breadcrumb should be sent.

</SpecSection>

<SpecSection id="error-sampler-hook" status="candidate" since="1.1.0">

### Error-Sampler Hook

SDKs **MAY** implement an `error_sampler` callback that decides the sample rate of an individual error event, mirroring `traces_sampler` for transactions.

The callback receives the event and, on platforms that support it, the hint. It returns either a boolean, or a float between `0.0` and `1.0`. When `error_sampler` is configured, `sample_rate` **MUST** be ignored.

This hook **MUST** only apply to `error` events. Unlike `before_send`, it is a sampling mechanism rather than a developer-controlled filter, so it **MUST** run at the sampling step of the [event pipeline](/sdk/foundations/client/#event-pipeline). An event it samples out **MUST** still update the session, and SDKs **MUST** record it with the `sample_rate` discard reason.

</SpecSection>

<SpecSection id="callback-error-isolation" status="candidate" since="1.1.0">

### Callback Error Isolation

A failing user callback **MUST NOT** break the host application. Where the language can recover from an error raised in a called function (`try`/`catch`, `rescue`, `recover`, `catch_unwind`), SDKs **MUST** invoke every user-provided callback inside that boundary, covering every non-local exit the language permits. A rejected promise, future, or task **MUST** be handled like a synchronous raise.

On failure, SDKs **MUST** emit an error-level [internal log](/sdk/foundations/client/configuration/#debug-mode) naming the callback, **MUST NOT** re-throw, and **MUST NOT** capture the error as an event or attach it to the item. See [Never capture your own exceptions](/sdk/getting-started/principles/#never-capture-your-own-exceptions). SDKs **MAY** re-throw in a non-default test mode documented to surface SDK failures.

A failure is not a return value, so SDKs **MUST NOT** infer a drop or a pass from it:

| Callback | On failure | Client report |
|---|---|---|
| `before_send` | Drop the event | `before_send`, category `error` |
| `before_send_transaction` | Drop the transaction | `before_send`, category `transaction` (plus [span outcomes](/sdk/telemetry/client-reports/#span-outcomes)) |
| `before_send_log` | Drop the log | `before_send`, category `log_item` |
| `before_send_metric` | Drop the metric | `before_send`, category `trace_metric` |
| `before_send_feedback` | Drop the feedback | `before_send`, category `feedback` |
| `before_send_check_in` | Drop the check-in | `before_send`, category `monitor` |
| `before_breadcrumb` | Drop the breadcrumb | None |
| `before_send_span` | Emit the span, discarding the return value | None |
| Event processor | Drop the event | `event_processor`, category of the item |
| `traces_sampler` | Fall back as if unconfigured | `sample_rate` if sampled out |
| `profiles_sampler` | Fall back as if unconfigured | `sample_rate` if sampled out |
| `error_sampler` | Fall back to `sample_rate` | `sample_rate` if sampled out |

Filters drop because a callback that failed part-way may not have applied the redaction the user wrote it to apply. `before_send_span` keeps the span because it is specified as enrichment, not filtering. [`ignore_spans`](/sdk/telemetry/spans/filtering/) filters spans. Samplers **MUST** fall back to the behavior they would have used had no sampler been configured, including any inherited decision that takes precedence over the static rate, and **MUST NOT** substitute `0.0` or `1.0`.

For the callbacks that keep the item, SDKs **SHOULD** pass a defensive copy so a partially mutated item can be restored. Where copying is impractical, SDKs **MUST** emit the item as it stands and **MUST NOT** apply any merge its own spec requires, such as the [`before_send_span` merge](/sdk/telemetry/spans/scrubbing-data/#scrubbing-data-with-beforesendspan).

A failure **MUST NOT** produce a billed event of any type. A dropped item **MUST** be reported exactly as it is on an explicit drop, and **MUST NOT** use a reason the callback could not otherwise produce; isolating a callback without reporting the loss is a conformance failure. Sampler failure is not distinguishable from ordinary sampling; reporting it would need a new discard reason, and `internal_sdk_error` is not a substitute because [SDK bugs are out of scope for client reports](/sdk/telemetry/client-reports/#discard-reasons).

This section does not apply to pure C and C++ built without exceptions, or to Rust built with `panic = "abort"`, which cannot isolate a failing callback.

</SpecSection>
