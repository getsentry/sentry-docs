<SpecMeta />

SDKs can track feature flag evaluations and attach them to error events and spans, so users can see which flags were in effect when an error happened or a span ran.

## Scope

This spec applies to SDKs that track feature flag evaluations. Tracking evaluations is optional.

## Definitions

- **Evaluation**: a flag name and the boolean result it evaluated to.
- **Flag provider**: a third-party feature flag SDK, such as LaunchDarkly or OpenFeature.

## Requirements

<SpecSection id="feature-flag-tracking" status="stable" since="2.0.0">

### Tracking Feature Flag Evaluations

**Error events.** Evaluations recorded on a scope **SHOULD** be attached to error events captured with that scope. Attached evaluations **MUST** follow the [Feature Flag Context](/sdk/foundations/envelopes/event-payloads/contexts/#feature-flag-context) schema. An event **SHOULD** contain only the latest evaluation of each flag, and only for the 100 most recently evaluated flags.

When a scope is forked, events captured with the new scope **SHOULD** include the evaluations recorded on the original scope before the fork. Evaluations recorded on the new scope **SHOULD NOT** appear in events captured with the original scope.

**Spans.** Evaluations recorded while a span is active **SHOULD** be added to that span. An evaluation added to a span **MUST** be a span attribute with the key `flag.evaluation.<flag name>` and the result as its value, following the [Span Data Conventions](/sdk/telemetry/traces/span-data-conventions/#flags). A span **SHOULD** contain only the first 10 flags evaluated while it is active.

</SpecSection>

<SpecSection id="add-feature-flag" status="stable" since="2.0.0">

### The `add_feature_flag` API

SDKs **SHOULD** expose a public `add_feature_flag` function, or a platform-idiomatic equivalent such as `addFeatureFlag`, that records an evaluation on the current scope.

The function **SHOULD** accept a string flag name and a boolean result. It **MUST NOT** record an evaluation whose result is not a boolean.

</SpecSection>

<SpecSection id="clear-feature-flags" status="stable" since="2.0.0">

### The `clear_feature_flags` API

SDKs **MAY** expose a public `clear_feature_flags` function on the scope, or a platform-idiomatic equivalent such as `clearFeatureFlags`. When called, it **MUST** remove all evaluations recorded on that scope, so they are no longer attached to events captured with it. It **MUST NOT** affect evaluations recorded on parent or sibling scopes.

</SpecSection>

<SpecSection id="feature-flag-integrations" status="stable" since="2.0.0">

### Integrations

A flag provider integration **SHOULD** record every evaluation made through the flag provider on the current scope, as if `add_feature_flag` had been called with the flag name and result.

</SpecSection>
