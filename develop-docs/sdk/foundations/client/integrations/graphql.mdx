GraphQL integrations instrument GraphQL clients and servers, so users can see which GraphQL operation caused an error, a span, or a breadcrumb. GraphQL servers report errors in the response body, often with a successful HTTP status code, so HTTP instrumentation alone misses them.

## Scope

This spec applies to SDK integrations that instrument a GraphQL client library or a GraphQL server library. Providing these integrations is optional.

## Definitions

- **Client integration**: an integration that instruments GraphQL requests sent by the application.
- **Server integration**: an integration that instruments GraphQL operations executed by the application.
- **Operation**: a single GraphQL query, mutation, or subscription. It has an **operation type** (`query`, `mutation`, or `subscription`) and can have an **operation name** and an **operation ID**.
- **Request payload**: the GraphQL request as defined by [GraphQL over HTTP](https://graphql.github.io/graphql-over-http/draft/#sec-Request), an object with `query` and, optionally, `operationName`, `variables`, and `extensions`.
- **Response payload**: the GraphQL response as defined by the [GraphQL spec](https://spec.graphql.org/October2021/#sec-Response-Format), an object with `data`, `errors`, or both.
- **GraphQL error**: an entry in the `errors` array of a response payload.

## Requirements

<SpecSection id="graphql-http-client" status="stable" since="2.0.0">

### HTTP Client Behavior

A client integration that sends requests over HTTP **SHOULD** behave as specified in [HTTP Client](/sdk/foundations/client/integrations/http-client/), except where this spec differs.

</SpecSection>

<SpecSection id="graphql-event-data" status="stable" since="2.0.0">

### Request and Response Data

These requirements apply to all data a client or server integration attaches.

An event whose `request.data` contains a request payload **MUST** set `request.api_target` to `"graphql"`.

When an event includes request data, `request.data` **SHOULD** be the request payload as a JSON object. When an event includes response data, `contexts.response.data` **SHOULD** be the response payload as a JSON object.

```json
{
  "request": {
    "api_target": "graphql",
    "data": {
      "query": "query GetUser($id: ID!) { user(id: $id) { name } }",
      "operationName": "GetUser",
      "variables": { "id": "1" }
    }
  },
  "contexts": {
    "response": {
      "type": "response",
      "status_code": 200,
      "data": {
        "data": { "user": null },
        "errors": [{ "message": "User not found", "path": ["user"] }]
      }
    }
  }
}
```

An integration **MUST NOT** attach `request.data` or `contexts.response.data` unless the user's settings allow the SDK to send request or response bodies. It **MUST NOT** set the `graphql.document` span attribute unless the user's settings allow the SDK to collect GraphQL documents. These settings are `sendDefaultPii` or, where supported, the `httpBodies` and `graphQL` options of [Data Collection](/sdk/foundations/client/data-collection/).

Reading a request or response body **MUST NOT** prevent the application from reading it.

</SpecSection>

<SpecSection id="graphql-client-errors" status="stable" since="2.0.0">

### Client Error Capture

When failed request capture is enabled (`captureFailedRequests` in HTTP Client), a client integration **SHOULD** capture an error event for each response whose response payload contains a GraphQL error and whose URL matches `failedRequestTargets`. It **SHOULD** do so even when the HTTP status code is not in `failedRequestStatusCodes`.

The event's `fingerprint` **SHOULD** be the operation name, the operation type, and the HTTP status code, in that order, so that errors are grouped per operation:

```json
{
  "fingerprint": ["GetUser", "query", "200"]
}
```

</SpecSection>

<SpecSection id="graphql-performance-server" status="stable" since="2.0.0">

### Server Instrumentation

**Errors.** When an exception raised by application code, such as a resolver, causes a GraphQL error, a server integration **SHOULD** capture an error event for it. The event **SHOULD** include the request payload and the response payload, subject to [Request and Response Data](#graphql-event-data).

**Spans.** When tracing is enabled, a server integration **SHOULD** record a span for each operation it executes. The span:

- **SHOULD** use an op in the `graphql` category of [Span Operations](/sdk/telemetry/traces/span-operations/), such as `graphql.query`.
- **SHOULD** have a name that contains the operation type, and **MAY** add the operation name, such as `query GetUser`.
- **SHOULD** have the `graphql.operation.type` and, if known, `graphql.operation.name` attributes defined by the [OpenTelemetry GraphQL semantic conventions](https://opentelemetry.io/docs/specs/semconv/graphql/graphql-spans/).
- **MAY** have the `graphql.document` attribute, subject to [Request and Response Data](#graphql-event-data).

When the operation name is known, the transaction that contains the operation **SHOULD** include the operation name in its name.

A server integration **MAY** also record child spans for resolvers (also called [data fetchers](https://www.graphql-java.com/documentation/data-fetching/)) and for [data loaders](https://github.com/graphql/dataloader).

</SpecSection>

<SpecSection id="graphql-performance-client" status="stable" since="2.0.0">

### Client Spans

When tracing is enabled, the span that a client integration records for a request, or the HTTP client span it enriches, **SHOULD**:

- Have a name that contains the operation type and, if known, the operation name.
- Have the `graphql.operation.type` and, if known, `graphql.operation.name` attributes defined by the [OpenTelemetry GraphQL semantic conventions](https://opentelemetry.io/docs/specs/semconv/graphql/graphql-spans/).

When both a client integration and an HTTP client integration instrument the same request, the SDK **SHOULD NOT** record more than one span for it.

</SpecSection>

<SpecSection id="graphql-breadcrumbs" status="stable" since="2.0.0">

### Breadcrumbs

Client and server integrations **SHOULD** record a breadcrumb for each operation. When known, its `data` **SHOULD** include:

- `operation_name`: the operation name
- `operation_type`: the operation type
- `operation_id`: the operation ID

When both a client integration and an HTTP client integration instrument the same request, the SDK **SHOULD NOT** record more than one breadcrumb for it.

</SpecSection>

## Implementation Guidance

_This section is non-normative._

**Why `api_target` matters.** When data scrubbing is enabled for a project, Relay replaces the values of `variables` in `request.data` with `[Filtered]` and scrubs the matching values in `contexts.response.data`. It only does this when `request.api_target` is `"graphql"` and both fields are JSON objects. Otherwise, GraphQL variables reach Sentry unscrubbed.

**Detecting GraphQL errors.** The Java Apollo integration checks the response body for an `errors` array with a regex, without parsing it:

```kotlin
val regex = "(?i)\"errors\"\\s*:\\s*\\[".toRegex()

// [body] is the stringified GraphQL response body
if (regex.containsMatchIn(body)) {
    // capture the error
}
```

Some frameworks expose the response as a stream that can only be read once. Integrations peek at or clone such streams before reading them, so the application still receives the full body.

**Choosing where to hook in.** Integrations typically use the hooks the GraphQL library provides, such as GraphQL Java's [`Instrumentation`](https://github.com/graphql-java/graphql-java/tree/master/src/main/java/graphql/execution/instrumentation) or Apollo interceptors. Where there are none, SDKs patch the library or, as a last resort, detect GraphQL requests in the transport layer, for example by URL path or request body shape. When both the GraphQL library and the HTTP transport are instrumented, the JavaScript `graphqlClientIntegration` adds GraphQL data to the existing HTTP span and breadcrumb instead of recording new ones.

**Breadcrumb types and categories.** The Java GraphQL server integration and the .NET GraphQL client set breadcrumb `type` to `graphql` and `category` to the operation type, or to `graphql.operation` when the type is unknown. The Java SDK also records breadcrumbs for resolvers, with category `graphql.fetcher` and `path`, `field`, `type`, and `object_type` in `data`, and for data loaders, with category `graphql.data_loader` and `keys`, `key_type`, `value_type`, and `name` in `data`. GraphQL documents can be large enough to push an event over the size limit, which is why these SDKs leave them out of breadcrumb `data`.
