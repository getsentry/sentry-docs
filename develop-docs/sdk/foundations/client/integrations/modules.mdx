The Modules integration attaches the libraries an application uses, and their versions, to events. Sentry shows them in the event details, so users can spot dependency-related issues.

## Requirements

<SpecSection id="event-enrichment" status="stable" since="2.0.0">

### Event Enrichment

SDKs **SHOULD** enable the Modules integration by default.

The integration **SHOULD** attach modules to events. Attached modules **MUST** be in the event's [`modules` field](/sdk/foundations/envelopes/event-payloads/#optional-attributes), as a map from module name to version string.

</SpecSection>

<SpecSection id="module-sources" status="stable" since="2.0.0">

### Module Sources

The `modules` field **SHOULD** list the libraries installed in or loaded by the application, each with the version actually in use.

</SpecSection>

<SpecSection id="event-type-filtering" status="stable" since="2.0.0">

### Event Type Filtering

SDKs **MAY** omit modules from event types where they are less useful, such as transactions, to reduce payload size.

</SpecSection>

## Implementation Guidance

_This section is non-normative._

How to discover modules depends on the platform. Common sources are package manager metadata (such as `importlib.metadata` in Python or `package.json` in Node.js), the runtime's module cache (such as `require.cache` in Node.js CJS), and module lists injected at build time, for bundled environments where runtime discovery is incomplete. When SDKs combine sources, the version from the more specific source, such as a lockfile or the runtime cache, is usually the one in use.

Installed packages rarely change while a process runs, so SDKs typically collect the module list once and cache it, rather than collecting it for every event.
