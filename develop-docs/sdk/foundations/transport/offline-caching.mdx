## Overview

Also known as "Buffer to Disk". SDKs write envelopes to disk before attempting to send, so that they can be retried in the event of a temporary network failure. SDKs **MUST** implement a cap on the number of stored envelopes and **SHOULD** implement a cap on their total size, as described in [Cache Limits](#cache-limits). This feature is mostly useful on mobile and desktop apps, where stable connectivity is often not available.

## Cache Limits

Envelope sizes vary widely. Most are a few kilobytes, but envelopes with screenshots, view hierarchies, or other attachments can be several megabytes. A limit on the number of envelopes alone doesn't bound how much disk space the cache uses, so SDKs **SHOULD** also support a limit in bytes.

### Options

| Option | Type | Default | Description |
|---|---|---|---|
| `max_cache_items` | `int` | `1000`, or `30` if the SDK doesn't support `max_cache_size` | Maximum number of envelopes in the cache. **MUST** be supported. |
| `max_cache_size` | `int` | `536870912` (512 MiB) | Maximum total size of the cached envelopes, in bytes. **SHOULD** be supported. |

SDKs **SHOULD** use the platform's naming convention, for example `maxCacheSize` or `MaxCacheSize`. SDKs **SHOULD** use a 64-bit integer type for `max_cache_size` where the platform has one, so users can set limits above 2 GiB.

With only `max_cache_items`, the cache can grow to 30 envelopes of up to 200 MiB each, the largest envelope Relay accepts (see [Size Limits](/sdk/foundations/envelopes/#size-limits)). The 512 MiB default for `max_cache_size` bounds disk usage to a predictable amount while still fitting one envelope of the maximum size.

SDKs that support `max_cache_size` use it as the primary limit and raise the `max_cache_items` default to `1000`. Thirty envelopes fill up quickly on a device that's offline for a while, for example with session updates, log batches, or replay segments, while 1000 still bounds how many files the SDK has to manage and send once the device is back online. SDKs without `max_cache_size` keep `30`, because the count limit is the only bound on their disk usage.

Setting either option to `0` disables caching: the SDK **MUST NOT** write envelopes to the cache and handles each envelope as described in [Envelopes Larger Than the Limit](#envelopes-larger-than-the-limit).

To remove a limit, users set the option to the platform's maximum integer value, for example `Int.MAX_VALUE`, `Long.MAX_VALUE`, `UInt.max`, or `SIZE_MAX`. This lets users rely on only one of the limits. For example, users who care about disk usage rather than the number of envelopes can set `max_cache_items` to the maximum value and keep `max_cache_size`.

If a user sets a negative value for either option, SDKs **MUST** ignore it, use the default, and log a warning in debug mode.

### Enforcing the Limits

The two limits apply together. The cache is within its limits only when both are satisfied, so exceeding either one triggers eviction.

Before writing a new envelope to the cache, SDKs **MUST** delete the oldest cached envelopes until:

- the number of cached envelopes plus one is at most `max_cache_items`, and
- the total size of cached envelopes plus the size of the new envelope is at most `max_cache_size`.

SDKs **SHOULD** also enforce both limits when the SDK initializes. The cache can exceed them after an app update lowers a limit, after an SDK update introduces `max_cache_size`, or after envelopes were written without enforcement (see [Crash Handling](#crash-handling)).

SDKs **SHOULD NOT** list the cache directory or read file metadata for every cached envelope on each write. Instead, SDKs **SHOULD** build an index of the cached envelopes (for example, file name, size, write time, and maximum age) when the SDK initializes, and keep it up to date as they write and delete envelopes. With up to 1000 envelopes, scanning the directory on every write is too slow.

### Maximum Age

Sentry's retention period limits how long cached data is useful. Relay corrects error timestamps older than the project's retention period to the time it received them, and rejects logs, spans, and trace metrics older than their retention period. SDKs **SHOULD** delete cached envelopes that are older than a fixed maximum age:

- **90 days** for envelopes that contain an event item, such as `event`, `transaction`, or `feedback`.
- **30 days** for all other envelopes, for example those containing only logs, spans, trace metrics, sessions, replays, profiles, check-ins, or client reports.

The maximum age isn't an option. SDKs **MUST NOT** expose it to users.

- The age of an envelope is the time since it was written to the cache, for example the file's modification time.
- An envelope with items of different types gets the longest maximum age of its items, so an event isn't deleted because it shares an envelope with a log.
- SDKs **SHOULD** determine the maximum age when they write the envelope and record it in the index or the file name, so they don't have to parse envelopes later. SDKs **MAY** read the envelope's item headers when they build the index at initialization.
- SDKs **SHOULD** delete expired envelopes when the SDK initializes, and **MAY** also delete them at other times, such as before writing an envelope.
- When an envelope is deleted because it's too old, the rules in [Eviction Order](#eviction-order) for client reports and session integrity apply.

### Measuring Size

- The size of an envelope is the size of its file on disk, as reported by the file system. If the SDK compresses envelopes before writing them, the compressed size counts.
- Only cached envelope files count toward either limit. Files the SDK keeps in the cache directory for other purposes, such as session files, crash markers, or another SDK's data (for example, a native SDK's database directory), **MUST NOT** count toward the limits and **MUST NOT** be deleted to satisfy them.
- SDKs **SHOULD** read file sizes from file system metadata and **SHOULD NOT** read or parse envelopes only to measure them.

### Eviction Order

SDKs **MUST** delete envelopes from oldest to newest, ordered by the time they were written to the cache, and **MUST** delete only as many envelopes as needed to satisfy both limits.

When an envelope is deleted to satisfy either limit or the [Maximum Age](#maximum-age), SDKs:

- **MUST** record a [client report](/sdk/telemetry/client-reports/) with the discard reason `cache_overflow` for the items in the deleted envelope.
- **MUST** preserve session integrity: if the deleted envelope contains a session update with `init: true`, the SDK **MUST** move the `init` flag to the next remaining session update for the same session, so release health stays correct.

### Envelopes Larger Than the Limit

If a single envelope is larger than `max_cache_size`, it can never fit in the cache. The same applies to every envelope when either option is `0`. In that case, SDKs:

- **MUST NOT** delete other cached envelopes to make room for it.
- **MUST NOT** write it to the cache.
- **SHOULD** still try to send it directly without persisting it, if the transport supports that. If the SDK can't send it, it **MUST** discard it and record a client report with the discard reason `cache_overflow`.
- **SHOULD** log a warning in debug mode that the envelope exceeded `max_cache_size`, unless caching is disabled because an option is `0`.

### Migrating Existing SDKs

Enabling `max_cache_size` by default changes behavior for existing users, because caches that were bounded only by `max_cache_items` can now evict envelopes earlier. Raising the `max_cache_items` default to `1000` lets the cache hold more envelopes than before. Deleting envelopes by [Maximum Age](#maximum-age) removes data that some SDKs currently keep longer; for example, sentry-cocoa currently deletes all envelopes after 90 days. SDKs that currently treat `0` as "no limit", such as sentry-native's `cache_max_items` and `cache_max_size`, also change behavior when they adopt `0` as "cache nothing". SDKs **SHOULD** ship these changes in a major version.

### Crash Handling

Writing to the cache while the app crashes is time-sensitive, and some crash handlers are restricted to async-signal-safe operations. When writing an envelope from a crash handler, SDKs **MAY** skip enforcing the limits and enforce them the next time the SDK initializes. Because eviction is oldest-first, the crash envelope is the newest and is deleted last.

## Dealing With Network Failures

When SDKs receive an `HTTP 2xx` status code response from Sentry, they **MUST** consider it as a successful send.

If Sentry returns an `HTTP 4xx` or `HTTP 5xx` status code, SDKs **MUST** discard the envelope and record a [client report](/sdk/telemetry/client-reports/#network-failure-recording) as specified in the client reports spec.

### HTTP 413 Content Too Large

For an [`HTTP 413 Content Too Large`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/413) response, SDKs:

* **MUST** discard the envelope and record a [client report](/sdk/telemetry/client-reports/#network-failure-recording).
* **MUST NOT** retry sending the envelope.
* **SHOULD** log an error, informing users that the envelope was discarded due to size limits.
* **MAY** add information from the response body to the logged error. If doing so, SDKs **MUST** be aware that Relay can change or remove information in the response body for an `HTTP 413` at any time without notice.

### HTTP 429 Too Many Requests

For an [`HTTP 429 Too Many Requests`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/429) response, SDKs:

- **MUST** respect the [rate limiting rules](/sdk/foundations/transport/rate-limiting/), such as correctly parsing the retry-header.
- **MUST** discard the envelope, but **MUST NOT** record a [client report](/sdk/telemetry/client-reports/#network-failure-recording), because the upstream already does this.
- **MUST NOT** retry sending the envelope.

### Network Errors

SDKs **MAY** retry sending the envelope when a network error occurs, such as:

* Connection timeout
* DSN resolution failure
* Connection reset by peer

When other failures occur, like those caused by processing the file in the SDK itself, SDKs **MUST** discard the envelope and record a [client report](/sdk/telemetry/client-reports/#network-failure-recording) with the discard reason `internal_sdk_error`. Otherwise, the SDK might end up in an endless retry loop.

See the [Client Reports — Network Failure Recording](/sdk/telemetry/client-reports/#network-failure-recording) spec for the full set of client report recording requirements for each HTTP status code.

## Additional Capabilities

SDKs **SHOULD** retry sending envelopes once the device is back online, when such notification exists in the platform.

Once the device is back online, the SDK is likely going to empty its disk queue in a quick burst of requests. This can trigger abuse filters in Sentry. To account for that, SDKs **SHOULD** add a small delay between cached envelope sends. A recommended value is 100 milliseconds.

If the SDK is being [rate-limited](/sdk/foundations/transport/rate-limiting/), which causes the SDK to drop any envelope that reaches its HTTP transport, SDKs **SHOULD** stop consuming the disk cache until the `Retry-After` timeout is reached or the app restarts.
