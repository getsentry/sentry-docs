SDK specs define what SDKs do, not how they do it. This spec builds on [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and adds only what is specific to Sentry SDK specs.

## Scope

This spec applies to specs. Its [Legacy Specs](#legacy-specs) section also applies to SDKs that implement legacy specs. Status, versioning, and changelogs are covered by [Spec Lifecycle](/sdk/getting-started/standards/spec-lifecycle/).

## Definitions

- **Spec**: a page under `develop-docs/sdk/` with `spec_id` frontmatter.
- **Requirement**: a statement in a spec that uses, rather than mentions, an RFC 2119 keyword written in uppercase, such as "MUST", "SHOULD", or "MAY".
- **Non-normative content**: anything in a spec that is not a requirement.
- **Externally observable behavior**: behavior whose conformance can be determined without inspecting the implementation's internals. For an SDK, conformance is determined using only its public API, the data it sends, its calls into user code, its effects on the host application, and its responses to inputs.
- **Legacy spec**: a spec without `spec_guidelines` in its frontmatter.

## Requirements

<SpecSection id="keywords" status="draft" since="0.1.0">

### Keywords

Requirement keywords have the meaning defined in RFC 2119. Keywords **SHOULD** be bold. A keyword that is mentioned rather than used **SHOULD** be put in quotes. Non-normative content **SHOULD NOT** state obligations with lowercase "must", "should", "may", or phrases such as "needs to".

</SpecSection>

<SpecSection id="observable-behavior" status="draft" since="0.1.0">

### Observable Behavior

Requirements **MUST** only describe externally observable behavior. When a requirement is written as steps, only its observable result is required.

</SpecSection>

<SpecSection id="requirement-levels" status="draft" since="0.1.0">

### Requirement Levels

Requirements **MUST** follow [Section 6 of RFC 2119](https://www.rfc-editor.org/rfc/rfc2119#section-6):

> Imperatives of the type defined in this memo must be used with care and sparingly. In particular, they MUST only be used where it is actually required for interoperation or to limit behavior which has potential for causing harm (e.g., limiting retransmisssions) For example, they must not be used to try to impose a particular method on implementors where the method is not required for interoperability.

In addition, requirements **MAY** specify an SDK's public API. Such requirements **SHOULD** allow SDKs to adapt names, signatures, and types to their platform's conventions.

"SHOULD" is the default requirement level. "MUST" and "MUST NOT" **SHOULD** only be used where no SDK could have a valid reason to deviate. Authors **SHOULD** assume such a reason could exist unless shown otherwise.

A requirement that most SDKs do not implement yet **SHOULD** be placed in a `draft` or `candidate` section (see [Spec Lifecycle](/sdk/getting-started/standards/spec-lifecycle/)), not weakened.

</SpecSection>

<SpecSection id="structure" status="draft" since="0.1.0">

### Structure

A spec **SHOULD** contain, in this order: a short introduction, Scope (optional), Definitions (optional), Requirements, and Implementation Guidance (optional), followed by the changelog required by Spec Lifecycle. Non-normative content **SHOULD** be kept to a minimum and, apart from the introduction and brief examples, placed in Implementation Guidance. Implementation Guidance **SHOULD** only describe proven patterns that are not documented elsewhere.

</SpecSection>

<SpecSection id="legacy-specs" status="draft" since="0.1.0">

### Legacy Specs

A spec that conforms to this spec **SHOULD** declare it with `spec_guidelines: writing-specs@<major.minor>`. A spec **MUST NOT** declare it unless the whole spec conforms. Legacy specs **SHOULD** display a notice linking to this section.

In a legacy spec, requirements on behavior that is not externally observable are not mandatory. SDKs **SHOULD** preserve the externally observable behavior that results from them. All other requirements in a legacy spec apply as written.

</SpecSection>

## Implementation Guidance

_This section is non-normative._

**The black-box test.** Ask: "Could I check this against a mock transport and the public API, without opening the SDK's source?" If not, it isn't a requirement. Usually the observable intent can be kept:

- "Use a single, centralized `ClientReports` component per client" → "Discarded events are reported in the client report of the client that discarded them."
- "Aggregate counts in a map keyed by reason and category" → "Each client report contains at most one entry per (reason, category) pair."

**The Section 6 test.** Ask: "Is this part of the public API? If not, would Sentry reject or misread data if an SDK ignored it, would SDKs fail to work together, or would users be harmed?" If none apply, it isn't a requirement: delete it, or keep it as guidance if it is a proven pattern. If one applies, use "SHOULD" unless no SDK could have a valid reason to deviate. Outside the public API, consistency across SDKs alone is not a reason for a requirement.

**Migrating a legacy spec.** Rewrite the observable intent as requirements, move proven guidance into Implementation Guidance, delete the rest, then add `spec_guidelines`.
